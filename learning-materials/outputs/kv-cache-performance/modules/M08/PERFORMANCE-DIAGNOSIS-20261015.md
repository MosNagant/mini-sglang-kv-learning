## 1. 整个工程现在能够回答什么

项目已覆盖地址与布局、尾部保护、公开调用契约、编译映射、微基准、多轮对照和真实模型接入。工程价值可以按下面这条证据链讲解：

```text
定义正确行为与支持范围
  → 实现并检查完整数据
  → 改变一个关键因素
  → 查看实际编译与启动方式
  → 同条件对照并保存全部轮次
  → 放回模型检查收益是否仍存在
  → 根据证据保留或放弃候选
```

“正确性通过”“编译改动生效”“特定配置更快”“整模型明显加速”是四种不同结论。前一种成立，不自动推出后一种。当前与原版的比较只针对固定mini-sglang提交中的具体实现，不能写成CUDA与Triton两种技术的普遍排名。

## 2. 六条路线的性能病历

| 路线 | 已观察到的现象 | 已确认的实现或编译事实 | 优先调查的假设 | 还不能下的结论 |
| --- | --- | --- | --- | --- |
| 单行Triton v1 | 既定微基准没有建立稳定超过原版的优势 | 每program处理一条K和对应V；真实地址由行距与indices决定 | 调用开销、program粒度、最终地址和访存指令差异 | “Triton天生比CUDA慢”或“已经打满带宽” |
| 1-Warp | 27号B256/D128三轮Graph均慢于4warp；B1/D64方向不稳 | D128由每线程1列改为4列，program数不变，产生更宽PTX访问 | 同时可调度的工作、指令组织、每program粒度等 | “肯定是occupancy低”“每线程寄存器增加” |
| 四行grouped | 30号B256/D128对v1三轮更快，B1/D64三轮更慢；对原版未稳定胜出 | B256的program数256→64；每program四行、仍4warp；有效总数据量没减少 | 每program工作量和总program数的权衡 | “数据规模越大越快”或“每次调用变成四次提交” |

| 固定形状访存隔离 | 36号布局、gap、顺序、起点与地址复用条件未达到事前三轮同向且每轮至少3%的Graph变化门槛 | 合法8字节输入偏移使grouped读取由向量形态变为更多标量读取 | 合并访问、对齐、缓存与运行波动 | “布局没影响”“PTX宽度就是DRAM事务大小” |

## 3. 第一课：1-Warp实验究竟说明了什么

26号完成限定正确性，27号做原版/4warp/1warp同场计时，28号保留实际编译对象。以下编译对比固定B256、D128、C1024、FP16、交错缓存、gap0、guard0，索引0..255。

| 实际项目 | 4warp v1 | 1warp候选 |
| --- | --- | --- |
| grid/program数 | 256 | 256 |
| 每program处理输入行数 | 1 | 1 |
| 每program线程数 | 128 | 32 |
| TTGIR sizePerThread | `[1]` | `[4]` |
| 每线程K列数、V列数 | 各1列 | 各4个连续列 |
| K/V PTX读取/写入 | `ld/st.global.b16` | `ld/st.global.v2.b32` |
| 实际编译元数据寄存器 | 14/thread | 14/thread |
| shared memory | 0字节 | 0字节 |
| n_spills原字段 | 0 | 0 |

以K的一行128元素为例：

```text
4warp：线程0处理列0，线程1处理列1，……，线程127处理列127
1warp：线程0处理列0..3，线程1处理列4..7，……，线程31处理列124..127
```

`v2.b32`表示每个活动线程的该次操作搬2×32bit，即8字节、4个FP16。数据类型仍然是FP16；最前面的`ld.global.b32`读取的是int32索引，不能与K/V数据访问混为一谈。

**每线程负责4列，不等于执行4倍访存指令。** 当前编译器已经把这些连续元素组织成向量访问。不能只凭工作量分配就宣布指令数量翻倍、依赖链变长；最终机器指令还需检查已保存cubin的反汇编。PTX中的向量宽度也不直接说明内存控制器完成了几次事务。

本次WIDTH与BLOCK_SIZE均128，没有尾列。保存PTX中的K/V谓词对应恒真值；它不构成D192尾部检查的证据。不能因为源码里写了mask，就认定每个特化始终执行相同的动态判断。

27号主口径为Graph，代表值是每进程30个区间均值的中位数，再取三个进程中位数的中位数：

| 配置 | 4warp代表µs | 1warp代表µs | 1warp相对4warp耗时变化 | 同轮方向 |
| --- | ---: | ---: | ---: | --- |
| B1/D64 | 0.958560 | 0.992640 | +3.555% | 1快、2慢 |
| B256/D128 | 1.144960 | 1.195360 | +4.402% | 3轮均慢 |

变化公式为`(候选耗时 / 参考耗时 - 1) × 100%`，正数代表变慢。不能把`1 - 参考/候选`误称为耗时增长比例。两个配置同时改变B和D，也不能据此单独归因行宽。

这一课能证明的是：**减少warp并产生更宽访问，没有在本次实验中带来预期收益。** 每线程寄存器均14，不支持“1warp每线程寄存器增加”的具体猜测；线程数不同又意味着不能据此推导两边每block资源或occupancy相同。shared为0，没有依据把这个内核的退化解释成shared-memory bank conflict。

证据：[27号计时复盘](../../reviews/20261010-m07-warps-timing-review.md)、[28号编译复盘](../../reviews/20261010-m07-warps-compile-review.md)、[4warp编译信息](../../logs/m07-warps-compile-results/run-20261010-123123-pgndtykl/frozen_v1/compiled.json)、[1warp编译信息](../../logs/m07-warps-compile-results/run-20261010-123123-pgndtykl/candidate/compiled.json)。两臂`compiled/`目录同时保留TTIR、TTGIR、LLIR、PTX、cubin。

注意：顶层`26-triton-store-candidate.py`是NUM_WARPS=4的准备模板；[实际运行快照](../../logs/m07-warps-compile-results/run-20261010-123123-pgndtykl/triton_store_candidate.py)才记录NUM_WARPS=1。复习时引用实际快照，不把模板当运行证据。

## 4. “冲突”和“等待”要分开调查

| 可能的机制 | 需要的证据 | 这次项目已知边界 |
| --- | --- | --- |
| shared-memory bank conflict | 相关shared访问及运行时冲突/访问指标 | 上述两份D128特化shared为0，不能拿这个机制解释它们 |
| 合并访问不理想 | 实际lane地址、最终访存指令、访问事务或sector相关指标 | TTGIR/PTX可帮助推导地址；尚未采对应运行时计数器 |
| 资源限制并发驻留 | block资源、硬件限制、理论和实际驻留/调度数据 | 仅有静态寄存器/shared字段，不等于测得occupancy |
| 主机提交或封装成本 | 主机路径分解、受控的入口消融、相同GPU工作的对照 | Eager与Graph差异是线索，不能直接把差值全部归因某段Python |

先做能够区分假设的最小观察。对1warp路线，可先离线反汇编现有cubin；若仍需运行时信息，再针对固定B256/D128两臂做定点profiling。计数器采集与主性能计时分开保存，微秒内核的短持续时间和工具重放开销必须记入限制。无需为了开始学习再重跑已经通过的26、27、28号。

## 5. 为什么实际提效从M08调用层开始

M08使用Qwen3-0.6B真实权重、RTX4070Ti、FP16、TP1；固定1请求、128输入token、32输出token。每次生成有28层×32次前向=896次KV写入。研究版是40号新适配器中的单行4warp内核，不是M07的grouped或full_groups。

42号端到端实验中，三轮`decode_graph`候选分别慢3.152%、慢1.300%、快0.836%；Eager分别慢19.068%、12.803%、23.022%。这些是完整离线`generate`墙钟时间，不能叫纯KV执行时间。Graph只覆盖decode，prefill仍Eager。

43号独立原版profile记录：

- KV的896个GPU内核持续时间累计0.812245ms。
- 全部11,976个GPU内核持续时间累计103.927254ms。
- KV份额为`0.812245 / 103.927254 = 0.781551%`。

**0.781551%是GPU内核持续时间之和中的份额，不是generate墙钟关键路径份额，也不是已经测得的Amdahl加速上限。** 跟踪插桩、Graph节点、WSL时间戳设置和操作重叠都需要区分；不能把这一个比值直接换算成整机最大提速。

它足以支持一个工程取舍：先调查Eager调用层和占比较大的操作，比继续只缩短KV中的几个指令更有根据。两类GEMV累计占内核时间和约83.345%，但模板名与具体模型调用/矩阵形状仍需对应，不能只凭名称宣布哪一层是根因。

相关证据：[M08完整结果及计时边界](RESULTS.md)、[43号原始结果](../../logs/m08-model-profile-results/run-uml9cxd9/result.json)、[43号审查](../../reviews/20261014-m08-model-profile-review.md)。

## 6. 44–46号事前设计：隔离适配开销，内核不变

以下为运行前的假设及计划，现已按该方向执行；并非当前待运行清单。完整实现、检查、三轮计时及局部收益/模型负结果另存于[实际结果](RESULTS-HOST-PATH-20261015.md)。

这是一项待验证假设：**同样的KV GPU工作，候选每次调用重复的Python元信息处理可能是Eager退化的一部分。** 40号源码确实每次调用`_validate_metadata`，随后生成启动参数并进入Triton调用；实际耗时占比尚未测定。

新实验先保持`m08_store_rows`的地址、mask、grid规则和4warp配置不变。不要同时加入grouped、修改warp或改变输入规模。这样若表现变化，才能首先调查入口路径的改变。

| 层次 | 计划回答的问题 | 必须保留的控制条件 |
| --- | --- | --- |
| CPU适配隔离 | 元信息解析/验证及参数构造大约花多少主机时间？ | 相同形状/stride描述；实际测量部分不做分配、同步或日志；若替换launch为记录/空操作，明确这只是CPU路径消融 |
| 相同内核的入口对照 | 减少重复适配后，Eager提交或整模型时间是否改善？ | 40号GPU计算不变；真实B从prefill128变decode1仍正确；原版作为独立参照保留 |
| 完整结果验证 | 入口优化有没有破坏地址、数据、空输入和Graph行为？ | 全缓存、未写区域、输入/indices、保存logits及生成token按实际覆盖核验；不能只看文本类似 |
| 同场性能确认 | 获益是否跨轮复现，Graph是否退化？ | 原版/旧适配器/新入口分别记录；同模型负载、政策、预热和计时边界；跨进程重复，保存全部数据 |

若引入内部可信入口，必须明确谁保证元信息、索引值和生命周期契约。不能把简单删掉公开入口检查写成“无条件等价优化”；不能把旧入口验证时间与新入口不含验证时间混成同一公共API能力。对模型集成，调用方可保证哪些条件，须由真实调用链证据支持。保留有检查的公共入口用于调试，不允许静默fallback、隐式连续化复制或不受支持布局直接进内核。

Graph replay不会重新执行捕获时的Python元信息检查。因此一个仅减少重复Python工作的改动，**更可能在Eager可见**；这只是预期，仍要实际测Graph和正确性。CPU消融结果不能直接从端到端差值相减得出精确贡献，提交与设备执行可能重叠。

事前决定：另存实际run、来源哈希、逐轮数据和结论，保留本设计及旧负结果。实际运行后，CPU封装消融下降约60%，但Eager整模型对旧版一快一慢一近似持平，未建立稳定改善。候选不晋升；不能改写为“GPU内核明显超越原版”。

## 7. 如何把每条路线讲成面试问题

复习顺序固定为“基础概念→机制追问→项目证据”。先用自己的话回答，再核对提示；这些提示本身不是掌握证明。

| 路线 | 基础概念题 | 底层机制追问 | 项目实际问题与回答边界 |
| --- | --- | --- | --- |
| 1warp | program、warp、线程分别是什么？ | 为什么每线程4列可能形成向量操作，而非4倍指令？ | 28号具体映射是什么？解释14寄存器/thread与shared0为何不能证明实际occupancy |
| grouped | grid与每program行数有什么关系？ | 减少program为什么也可能减少并行任务或增加单program工作？ | B256对v1三轮快但对原版不稳，如何报告两个不同参照？ |
| full_groups | constexpr条件与运行时判断有何不同？ | 寄存器18→14为什么不保证加速？ | 代表值快但三轮两次慢，为什么不能只引用SUMMARY？ |
| 访存布局 | width、stride、gap、K/V分离分别是什么？ | 同一warp的地址分布、对齐与最终事务有什么联系？ | 36号向量读取改变却无稳定Graph收益，下一项应补什么证据？ |
| 原版与v1 | 算子语义相同是否意味着实现分工相同？ | 原版每warp一行与v1每program一行怎样改变block/program组织？ | 为什么“我写Triton慢于这个CUDA实现”不能推广到语言优劣？ |
| M08 | Eager、Graph、GPU Event与CPU墙钟分别测什么？ | 为什么捕获后的Python开销与Eager每次调用不同？ | KV0.781551%能说明什么、不能说明什么？如何验证调用层优化？ |

一段可据证据复述的项目表达：

> 我参与了KV写入的Triton实现与验证，随后对比warp数、每program行数、完整组特化和访存条件。部分配置优于自己的v1，但没有稳定超过原版。项目进一步接入真实模型，验证缓存、token和抽查logits一致，发现Graph接近原版而Eager退化。我们保持GPU内核不变优化重复元信息处理，CPU局部消融耗时下降约60%，但完整模型三轮未稳定获益，因此没有替换默认后端。下一步需要把主要GEMV与实际调用/形状对应，继续按事实、假设和未验证部分分别记录。

其中“实现”“设计”“执行”“解释”要按实际个人贡献调整。原版、候选及工具由谁完成，在各历史日志中有记录；44–46实现、运行及审计由教练完成，不说成个人独立手写，不把CPU局部改善说成GPU或模型稳定提速。

## 8. 本轮判断标准

1. 有新证据才能升级归因：静态结构、运行指标和控制变量分别回答不同问题。
2. 优先让真实使用场景受益；教学微基准与整模型指标分开写。
3. 同时报收益和退化；每轮数据、失败和候选保留，不挑最好一次。
4. “CPU入口更轻”“KV内核更快”“模型生成更快”分别验收，不互相替代。
5. 当前设备是NVIDIA，AMD面试可以迁移实验方法；没有AMD实机性能结论。

本文整理已有证据、事前设计及实际结果入口；历史验收、默认后端和旧运行目录保留，本次新增资料尚未同步GitHub。
