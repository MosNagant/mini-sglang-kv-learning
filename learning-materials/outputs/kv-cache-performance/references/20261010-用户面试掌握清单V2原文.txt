## 三、GPU Memory Hierarchy——今天进步最大的模块

| 知识点 | 状态 | 依据 |
|---|---|---|
| Register | ✅ | 理解是线程私有的高速工作空间 |
| Shared Memory | ✅ | 理解是物理硬件，并按 Block 分配使用 |
| Shared Memory 作用域 | ✅ | 已理解不是 Warp 私有，而是 Block 内共享 |
| Shared Memory vs L1/L2 | ✅ | 已理解显式管理与硬件自动缓存的区别 |
| Data Reuse | ✅ | 能判断重复使用的数据更值得考虑 Shared Memory |
| Shared Memory 容量限制 | ✅ | 主动提出容量有限、不能全部放入的判断 |
| Shared Memory 与 Occupancy | 🟡 | 理解资源竞争，尚未进行定量计算 |
| L1 Cache | 🟡 | 理解自动缓存机制，尚未深入缓存命中分析 |
| L2 Cache | 🟡 | 理解跨 SM 共享，尚未深入访存路径 |
| Global Memory | ✅ 基础 | 理解存储大规模数据的作用 |
| Local Memory | 🟡 | 已学习定义，但容易与片上内存混淆，需复测 |
| Memory Coalescing | ⬜ | 刚开始讲解，尚未回答相关问题 |
| Bank Conflict | ⬜ | 已引入概念，尚未深入学习 |

### 这一部分你真正学到了什么？

最开始，你把 Shared Memory 理解成一种自动高速缓存。

现在已经能够区分：

**Register：** 每个线程自己的工作台。

**Shared Memory：** 同一个 Block 内多个线程共同使用的工作空间。

**L1：** 主要服务一个 SM 的硬件缓存。

**L2：** 多个 SM 共享的硬件缓存。

**Global Memory：** 大容量的 GPU 存储空间。

你还能够解释为什么 KV Copy 不一定值得使用 Shared Memory。

这是一个实质性的进步。

不过，**下一步必须开始研究真实地址和访存行为**，否则目前仍然主要停留在概念层面。

### 下一步：Memory Coalescing

我们刚刚停在一个非常重要的问题：

你的 KV Cache 写入使用：

```python
indices = [7, 0, 3]
```

三个 Program 分别向第 7、0、3 个缓存槽写数据。

**问题：虽然这些缓存槽的位置不连续，但是每个槽内部的元素连续排列，那么 Memory Coalescing 一定会受到破坏吗？为什么？**

这是我们接下来应该解决的第一个问题。

它会让你从目前的“理解 GPU 存储资源”，真正进入**分析 GPU 访存效率**的阶段。
