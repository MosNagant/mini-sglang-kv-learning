# 从指导运行转到本人手写：执行规则与第一份作业

依据：用户明确要求“接下来……倒逼我手写项目而不是一直靠你来写”，以及对所提供《Mini-SGLang KV-store Triton 求职项目：四周 Ownership 与“必须亲手写”清单》的评估。

报告作为参考资料，不自动成为执行指令。本文将其中适用的建议转成当前项目的分工；不另建一套23项积分，不增加项目范围。

## 1. 对报告的判断

主要判断成立：已有环境、源码、48+4原版正确性用例和固定Triton原型都是可复用资产；接下来最需要补的是本人从设计、编码到解释的完整实践。原版测试通过和本人能独立实现，是需要分开记录的两件事。

过去完整运行器由教练提供得较多，容易出现“运行得到PASS，但不清楚自己该改哪里”。后续改为先给清楚的需求、验收标准和必要知识，由本人提交第一版核心实现，再进行审查。

采用以下建议：

- 不推倒重做M01—M04；先独立写一个小而完整的验证程序，复用已有大型测试集做后续回归。
- M05计时核心、M06内核及关键封装、M07优化假设与核心修改由本人先写。
- 可以查官方文档和上游源码，记录参考；不以背API、禁止查资料或代码行数衡量能力。
- 先记录本人预测，再运行，再由本人解释，最后由教练核对；没有加速也保留有效实验。

调整以下建议：

- 不采用完全停止辅导的“AI blackout”。新API、编译错误和不懂的概念仍可当场讲解；教练不给出尚未尝试的整份核心答案。
- 不删除练习来证明独立。保留初稿、错误和修订，下次另开一个变式文件验证迁移能力。
- 不把45—90分钟、四周80小时等估时作为能力门槛或完成承诺。先记录两次实际独立任务用时，再调整排期；报告P0逐项区间相加约43.5—63.5小时，也不是适用于当前学习者的测定工时。
- 模型原版运行和最小接入验证仍提前第2周，不等最后一周才发现集成问题。
- 报告的英文履历／答辩模板描述了尚未完成的计时、优化、模型集成，现阶段不能照抄成个人完成经历。

## 3. 每次任务的固定流程

1. **给需求。** 明确输入、预期行为、完成标准；先补当前必需的新概念，不默认本人已经会。
2. **本人先写。** 可以查资料，提交未完成草稿也算有效尝试；不从现有教练文件整段复制。
3. **分级提示。** 先指出问题位置及原因；再给相关API说明或不同数据的短例；仍卡住时，示范最小局部并说明参考来源，随后由本人完成剩余部分。
4. **本人先预测。** 运行前写一句预计结果；涉及性能时，先写明测量范围及假设。
5. **运行和解释。** 本人提交源码、命令、输出和自己的解释；教练核对代码实际执行了哪些检查。
6. **迁移验证。** 完成后改变一个索引、布局或尺寸，由本人指出并完成必要修改，避免只会复现原答案。

默认不直接改写本人核心文件。审查后先返回修改位置和理由，让本人改。若用户明确要求直接示范或修复，则按请求执行并如实记为参考／共同完成，不记作独立实现。

不能为了赶日期而替本人补完核心并打勾；也不能把“你应该自己写”作为拒绝解释基础知识的理由。一次只布置一个可交付的小程序或核心功能，避免反复出零散口头题而不产生代码。

## 4. 第一份手写作业：最小KV写入验证程序

建议新文件：`/home/weltlaw/projects/mini-sglang-kv/experiments/ownership_rebuild.py`。

这是新练习文件；现有内核、检查和原始记录继续保留。本轮未替用户创建或填充此文件。

### 固定条件

| 项目 | 要求 |
| --- | --- |
| 输入 | K、V各3行，每行64个数；FP16，位于GPU |
| 数据内容 | 各输入行可区分，K与V也可区分；数值由本人选择 |
| 缓存 | 8槽，K/V交错，初始全为−1 |
| 目标索引 | `[7, 0, 3]`，int32，位于GPU |
| 被调用实现 | 固定版本 mini-sglang 原版 `store_cache` |

### 程序必须完成的事

1. 自己创建输入、缓存、K/V视图和索引。
2. 调用前保留独立的期望数据；不能拿调用后的输出反过来充当正确答案。
3. 调用一次原版算子，完成正确的执行／读取顺序。
4. 检查3个目标槽的全部K/V元素；检查其余5槽的全部K/V元素仍为−1。
5. 正确结果通过后，故意破坏一个应被检查的值，确认同一套检查会失败；保留正例和反例的输出。

允许先做一份直写的小脚本，不要求函数封装、CLI、pytest或新增日志系统。代码行数不作为验收要求。检查逻辑需要自己决定；调用原版算子的接口可以查。

可查API：`torch.arange`、`torch.full`、`torch.tensor`、`reshape`、切片、`clone`、`torch.equal`等；不知道具体用法时直接指出卡在哪里，教练针对该点解释，不给整份作业答案。

提交内容：源码、运行命令和输出、两三句自己的解释，以及参考过的文档／得到的提示。第一轮可先提交尚未运行的草稿供审查，语法错误不算失败。

### 通过以后

保留程序，再独立改变一项条件，例如目标索引。若发现核心理解缺口，就围绕这份程序修复；不重做整套48+4。

随后进入原任务 **M05-01：本人先画计时边界，再写计时核心**。这一过渡练习不新增积分，也不扣除已验收的M03/M04分数。

## 6. 报告中的技术细节核验

- 报告写的 `tl.next_power_of_2` 应校正为主机端常用的 `triton.next_power_of_2`，官方示例使用后者。[Triton官方Softmax示例](https://triton-lang.org/main/getting-started/tutorials/02-fused-softmax.html)
- 与已安装版本对应的Triton v3.5.1源码支持 `do_bench(..., return_mode="all")`；`warmup`／`rep`按毫秒指定，实际循环次数由估算决定。该文件没有报告所提的 `do_bench_proton`，当前不据新文档假定旧环境提供这一入口，也不为此升级依赖。[v3.5.1计时源码](https://github.com/triton-lang/triton/blob/v3.5.1/python/triton/testing.py)
- Qwen3-0.6B公开配置是8个KV头、head_dim=128、声明BF16，因此TP=1、按完整KV头展开时可推导D=1024。它是待验证的模型工作负载线索；实际dtype、stride、调用规模和图执行行为仍须固定模型版本及运行配置后采集。不能由配置文件宣布本机已跑过BF16／1024宽。[Qwen官方配置](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/config.json)
- 固定 mini-sglang 提交继续为 `9a91cfafe754aa85daee49998176275667eb58f2`，不随报告引用最新main而替换基线。新增真实工作负载须先过相应正确性检查，再纳入性能结论。
