## 成品要解决的问题

在固定 mini-sglang commit 9a91cfafe754aa85daee49998176275667eb58f2 上，研究 store_kv_cache 的写入路径：什么时候慢，哪些证据支持瓶颈判断，一个用户亲手实现的 CUDA 变体改变了什么，哪些输入受益、哪些回退，整机影响有多大。

主力硬件是用户的 RTX 4070 Ti。作品展示可迁移的性能工程方法；AMD/HIP 的知识对照单独说明，不能把 NVIDIA 实测写成 AMD 实测。

挑战目标仍为至少两个预先选定的中大 batch 形状上约 15% 稳定内核延迟下降，并报告全部形状与明显回退。是否达到该数字不决定实验诚实性；若未达到，保留证据并重估假设。不得为赶日期省略正确性、伪造计数器或挑选最好的一次。

## 第 1 周：09-29 至 10-05，建立可信的原版成绩

要回答：内核输入输出是什么，我们是否真的测到了目标操作？

09-30范围澄清：用户希望本周跑通第③CUDA层和第④推理框架层。按本项目第1周截至10-05，以KV写入这条路径为范围，目标是能运行、能独立解释、能验证并保存可复测的原版时间数据；不是在一周内掌握完整CUDA与全部框架。最小Python→CUDA执行已经有上游测试和08观察证据。接下来的验收仍是下列M03–M05，完整模型运行保持后期安排。用户承诺每周20小时以上，实际可用剩余时间未确认，因此这是合理冲刺目标而非进度保证。先让每段源码理解对应一个代码或验证产物，减少反复术语讲解。

1. 完成 L01 实际布局观察，对照测试与真实 mha_pool 的布局差异；用户推导行起点与字节量。
2. 阅读 store.py → store.cu 的启动和线程映射；用户画出一个小 batch 的输入行与目标行关系。
3. 用户写正确性初稿，覆盖唯一索引、未命中行保持不变、支持的边界和布局；非法输入与空 batch 是否支持先查代码契约。
4. 用户先提出计时步骤，再在助手提供的记录脚手架中实现；区分 JIT、调用、GPU 时间和同步。用重复测量保存原始样本、median、分位数/波动定义。
5. 固定 batch 为 1、4、16、64、256、1024、4096、16384；字节宽度由代码约束、真实布局和显存决定。预登记两个优化目标形状，不依据变体收益事后挑选。
6. 对 KV 工作负载采集一次 Systems trace 并解释可见事实；NCU 若仍不可用，记录指标缺失，并用可得到的启动信息、时间线、代码与对照实验建立证据。

交付：数据契约、正确性脚本、计时协议、环境快照、原版 CSV/JSON、KV trace 与初步问题清单。累计目标 30/100。

验收问法示例（届时只问 3–5 题）：给定真实 stride 如何找到某 token 的 V？未命中位置为何要检查？一个 GPU 事件测到的区间为何可能与 Python 调用耗时不同？有效写带宽的分子包括什么、不包括什么？

## 第 2 周：10-06 至 10-12，实现一个可解释的 CUDA 变体

要回答：哪一个具体瓶颈假设值得改变代码验证？

1. 用户基于第一周数据提出一个假设和可证伪预测；助手审核是否存在启动开销、布局、缓存复用等混杂因素。
2. 用户设计线程/warp/token 分工、地址计算、尾部保护，先写伪代码再写 CUDA C++ 初稿。不得先指定“多个 warp 一定更快”。

4. 原版与变体可显式切换，在相同独立正确性集上验证，修改前的原始基线保留。

交付：独立变体源码、设计说明、正确性结果和第一轮性能对照。累计目标 55/100。初轮变快不等于优化成功。

## 第 3 周：10-13 至 10-19，判断收益是否稳定且可解释

要回答：改善来自哪一项改变，换输入和重复运行后还成立吗？

1. 使用预定形状和相同输入/布局，交替运行原版与变体，多轮保存全部样本；测量轮次与统计规则先写入协议。
2. 分开比较连续/切片输入、目标索引分布、字节宽度、batch 与合理的缓存复用情境；一次改变一个因素。
3. 观察时钟、功耗、其他桌面 GPU 工作等可能的影响；可获取什么就记录什么，不要求锁时钟才允许实验。
4. 制作延迟、波动、speedup 和回退表；讨论有效写入带宽与物理 DRAM 流量的区别，明确 profiler 开销和时间戳精度限制。
5. 10-16 做一次方向检查：若收益不足，重新审查测量和假设，只选择一个有证据的新方向，保留原来的失败记录。

交付：原始数据、汇总脚本、消融图、瓶颈证据、收益与局限报告。累计目标 80/100。

验收：为何小 batch 和大 batch 结果不同；哪条证据支持因果解释；一组反例意味着什么；哪些结论不能从现有计数器证据得出。

## 30 分钟讲解结构

| 时间 | 内容 | 必须有的依据 |
| --- | --- | --- |
| 0–3 分钟 | 要解决的问题、KV 写入在推理中的位置 | 实际调用链和输入输出 |
| 3–8 分钟 | 原版数据布局与线程分工 | 源码、地址推导、小张量观察 |

| 14–20 分钟 | 瓶颈假设、CUDA 改动、消融 | 用户实现与能推翻假设的实验 |
| 20–25 分钟 | 哪些情境有效、哪里回退、整机影响 | 完整结果、误差/波动、端到端对照 |
| 25–30 分钟 | 限制、失败、AMD 迁移边界及追问 | 已测/未测区分和下一步证据需求 |

这不是要求背满 30 分钟术语。验收时会随机换一个尺寸、指向一行代码或质疑一张图，让用户重新推导。
