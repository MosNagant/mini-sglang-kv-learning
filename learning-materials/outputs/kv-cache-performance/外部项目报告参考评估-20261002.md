## 1. 两份计划的区别

| 项目 | 这份报告 | 我们当前的计划 |
| --- | --- | --- |
| 开发载体 | 新建受 SGLang 启发的独立算子库 | 固定版本 mini-sglang，替换其中的 KV 写入实现 |
| 核心算子 | RMSNorm、残差加法融合 RMSNorm、SiLU-and-Mul、RoPE | KV Cache 写入；参数化、布局适配、优化迭代 |
| KV 写入位置 | 后期扩展项，正文不同位置标为P1或P2 | 当前主项目 |
| 主要对照 | PyTorch eager、torch.compile、本人 Triton | 固定原版 CUDA、本人 Triton v1/v2；其他对照按需要补充 |
| 集成目标 | 小型 decoder block 演示 | mini-sglang 小模型实际调用与端到端A/B |
| 工时假设 | 四周120小时，约30小时/周 | 每周20小时以上，实际已用时间未记录 |
| 学习起点 | 默认能较快进入归约、精度、融合与工程工具 | Python基础基本会；PyTorch、指针/stride和Triton正在建立 |
| 硬件适配 | 有“硬件没有指定”的表述 | 已知 RTX 4070 Ti、WSL2、Torch 2.9.1+cu128、Triton 3.5.1 |

因此，它是一份可以借鉴的另一个项目方案。报告里的“约一百万元素”等题设也不是我们已经确定的工作负载；我们的配置应由算子约定、显存预算和模型实际调用共同决定。

120小时是报告作者的预算假设，没有经过你的实际学习速度验证。不能把它当成四周完成承诺，也不能在已有任务上直接再叠加120小时。

## 3. 已核验的技术内容和需要修正的地方

### 3.1 SGLang 的 compiler 对照案例有依据，但适用条件要保留

报告多次引用的相关案例可以在 [SGLang issue #21855](https://github.com/sgl-project/sglang/issues/21855) 找到：作者比较了部分 decode 区域的编译融合，报告了特定模型和配置下的收益，也列出了回退。实验使用 GB200、特定 SGLang 提交和 PyTorch nightly 2.12。

它支持我们增加一个问题：“编译器能否自动得到类似的改进？”不能据此推断我们的4070 Ti、当前软件版本和KV单算子也有相同收益。本次核验确认了公开报告的存在及条件，没有复现该实验。

在本项目中，原版 CUDA 保持主基线。PyTorch reference先承担正确性核对；`torch.compile`可在主对照稳定后作为额外实验。加入时必须保持相同写入语义、布局和计时范围，并单独处理编译、回退和缓存修改的影响。

### 3.2 `do_bench` 的计时口径需要改写

报告把 `do_bench` 的主结果描述为“end-to-end callable latency”，这个名称不够准确。对照我们正在使用的 [Triton 3.5.1源码](https://raw.githubusercontent.com/triton-lang/triton/v3.5.1/python/triton/testing.py)：

- 它使用设备事件测量区间；不能直接称为完整的CPU加GPU端到端耗时。
- `warmup=25`、`rep=100`表示以毫秒为单位的时间预算，内部估算循环次数。
- 正式采样前会清理缓存；这与重复访问同一批数据的热缓存实验条件不同。
- 极短调用的事件区间可能受主机提交间隙影响，也不应自动称为纯内核指令执行时间。

落到M05-01：分别定义设备事件区间、需要同步边界的整段调用耗时、后续模型端到端耗时。每张表标出方法和缓存策略；不同方法的数字分别报告。这里核验的是工具实现，尚未运行我们自己的性能测量。

### 3.3 边界测试值得采用，但不能机械套用数值容差

空输入导致错误启动的案例确有 [SGLang issue #23609](https://github.com/sgl-project/sglang/issues/23609) 和对应 [修复PR #23636](https://github.com/sgl-project/sglang/pull/23636)。这说明空输入行为应该进入接口约定。它不是我们当前KV实现已经存在相同错误的证据。

报告里的RMSNorm涉及浮点计算，需要讨论累加精度和容差。我们的KV写入是复制：对当前有限数值用例应检查精确一致，不能用宽松容差掩盖写错数据。若扩展NaN或位模式覆盖，再明确比较规则。150或250个参数化测试不是硬性能力门槛，覆盖了哪些错误更重要。

### 3.4 布局必须来自实际调用

练习中的缓存是K/V交错的，不能把“缓存行距=2×WIDTH”推广到所有场景。固定提交的 [mini-sglang MHAKVCache源码](https://github.com/sgl-project/mini-sglang/blob/9a91cfafe754aa85daee49998176275667eb58f2/python/minisgl/kvcache/mha_pool.py) 将K/V缓冲区分开，并在调用store时取对应层的视图。

因此M06传入真实stride、M08检查模型实参是必要工程工作。报告新增其他算子的建议不能代替这一步。

### 3.5 自动调优不能跳过状态和正确性检查

[Triton autotune文档](https://triton-lang.org/main/python-api/generated/triton.autotune.html) 说明调优会多次执行候选配置，并提供重置/恢复被修改数据的机制。

当前先手动比较少量配置、保留v1，再判断是否需要自动搜索。KV写入的重复执行是否等价，要按输入、索引、别名和缓存重置方式具体判断；不能照搬融合残差的处理方式。

## 5. 对“现在的KV复制会不会太简单”的客观判断

目前的固定小例确实不足以代表完整项目：它已经帮助你理解了寻址、读写和按索引检查，但还不能证明通用实现、性能分析或系统接入能力。

接下来同一个KV算子还要回答这些工程问题：两种布局如何适配；不同形状如何正确处理；什么情况下更慢；测量是否可信；改变program分工后是否改善；接入模型后有没有实际影响。这些都有明确的代码和实验产物，可以形成深入讲解的内容。

同时，KV复制对归约和数值计算的覆盖有限。报告提供了一个合理的后续补充候选：**RMSNorm，再视需要研究残差加法融合**。通俗地说，归约是把一整行数字合起来算出一个结果；融合是研究相邻步骤能否一起完成、减少中间数据搬运。这能补当前复制任务较少涉及的能力。

扩展门槛建议：原版基线、参数化KV正确性/首次对照完成，模型接入风险已摸清，并记录实际剩余工时后，再决定是否安排第二算子。它不计入现有100分，不作为为了凑30分钟而新增的硬指标；优先完成一个能够被追问的工程过程。
