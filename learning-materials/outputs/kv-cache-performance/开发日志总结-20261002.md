## 1. 我们到底在做什么

项目名称：**基于 mini-sglang 的 KV Cache 写入算子：Triton 实现、正确性验证与性能分析**。

现有算子的工作是：把已经计算好的 K、V，按照 `indices` 指定的目标槽，分别写入 K、V 缓存。当前实验调用算子时，输入和缓存已经在 GPU 上。这一步不负责生成 K/V，也不负责生成大模型的文字回答。

例如 `indices = [7, 0, 3]`：

| 输入行下标 pid | 目标槽 pos | 要做的操作 |
| --- | --- | --- |
| 0 | 7 | K[0] → K缓存[7]；V[0] → V缓存[7] |
| 1 | 0 | K[1] → K缓存[0]；V[1] → V缓存[0] |
| 2 | 3 | K[2] → K缓存[3]；V[2] → V缓存[3] |

完整作品要回答三个工程问题：**能否写对、与原版相比快慢如何、接入实际模型后有什么影响。** 当前已经建立了第一部分的原版验证基础，正在向正式测量推进。

## 5. 已经讲清楚的关键概念

| 名词 | 在本项目里的意思 |
| --- | --- |
| batch／B | 本次要写入多少行 K/V |
| width／D | 每行有多少个有效数；不是字节数 |
| FP16 | 每个数占2字节；D=64的一行数据占128字节 |
| stride／行距 | 从这一行开头到下一行开头跨过多少个元素 |
| gap | 本轮测试在输入有效行后额外留出的空间；不是用数值是否为0或−1来判断 |
| pid | 当前 Triton program 对应的输入行下标，从0开始 |
| pos | `indices[pid]` 中读出的目标槽编号 |
| pointer／指针 | 某块数据的起始位置；K、V指针可以有不同起点 |
| assert／断言 | 检查条件是否成立，不成立就报错，防止错误结果被当作成功 |

当前列连续的例子中：

```python
pos = indices[pid]
src_offsets = pid * input_stride + cols
dst_offsets = pos * cache_stride + cols
```

这里的偏移单位都是**元素**。如果要手算 FP16 的字节偏移，应把整个元素偏移乘2，不能只把列下标乘2。

例：连续64宽输入，`indices=[7,0,3]`、`pid=2`、列下标4：

- `pos = indices[2] = 3`。
- 源偏移：`2×64+4=132`元素，即`264`字节。
- 交错缓存行距128：目标偏移`3×128+4=388`元素，相对于对应 K/V 指针各自的起点。
- 定位源行是在算地址，不需要先遍历读取前两行。

### 布局、有效宽度与 gap

```text
交错缓存：K0 | V0 | K1 | V1 | K2 | V2 | ...
分离缓存：K0 | K1 | K2 | ...；V0 | V1 | V2 | ...
带空隙输入：有效行0 | gap | 有效行1 | gap | ...
```

| 布局条件 | D=64时的行距 | D=128时的行距 |
| --- | ---: | ---: |
| 连续输入，gap=0 | 64 | 128 |
| 本轮输入，gap=64 | 128 | 192 |
| 交错缓存 K/V 视图，无额外填充 | 128 | 256 |
| 分离连续缓存 K/V 视图 | 64 | 128 |

输入是否有 gap，与缓存是否交错是两个不同的测试条件。仅改变缓存布局时，应改变目标寻址；输入未变，就不需要改变源寻址。`src_stride` 和 `dst_stride` 没有固定的二倍关系。

### 启动内核与检查结果

```text
准备5行输入和5个目标索引
        ↓
一次启动 grid=(5,)，提交5个 Triton program
        ↓
GPU执行，等待完成
        ↓
Python for循环逐行检查已写入的 K/V
```

一起提交不保证5个 program 在硬件上同时执行。检查循环也不负责启动这5次搬运。旧日志的“2/2”表示两个实现各通过一个用例，不表示只搬了两行。

自己写过的关键检查是：

```python
for pid, pos in enumerate(target_rows):
    assert torch.equal(k_cache[pos], expected_k[pid])
    assert torch.equal(v_cache[pos], expected_v[pid])
```

它比较完整行的数据内容；不同地址中的内容也可以相等。完整测试集合另有检查未命中槽、输入、空隙及索引是否被意外修改的代码。

## 6. M04到底验证了什么

最新成功运行：`run-20261002-150548-_gy98gbd`。本轮对象为**固定提交的原版 CUDA**。

| 变化维度 | 实际覆盖 |
| --- | --- |
| 输入行数 B | 1、2、3、4、5、17 |
| 有效行宽 D | 64、128 |
| 缓存布局 | 交错、分离 |
| 输入额外 gap | 0、64元素 |
| 数据类型 | K/V及缓存 FP16；索引 int32 |
| 缓存容量 | 32槽；使用唯一、合法索引，包含首尾位置 |

非空矩阵为 **6×2×2×2=48个 GPU 用例**。另外，两个宽度×两种布局形成4个空输入适配器用例。

每个非空用例检查：目标槽的全部 K/V 数值正确；未命中槽没被修改；输入及其底层空隙、索引保持不变。期望数据在执行前独立准备，每例使用新缓存并保存完整数据。

还故意制造9类数据错误，确认检查能拒绝错行、漏写末列、K/V混用及意外修改等情况；另有6类无效配置在 CPU 端被拒绝，包括负索引、越界、重复、数量不符、容量不合法和不支持宽度。

成功摘要：

```text
M04_ORIGINAL_PASS: 48 GPU cases + 4 empty adapter cases; all values and backing storage checked.
```

离线复核重新构造了52例的完整期望数组，并核对23个源码哈希，结果为 `OFFLINE_REVIEW_PASS`。复核没有重跑 GPU。

结论边界：

- 空输入由外部适配器跳过调用，不能据此宣称原版 CUDA 支持零大小启动。
- 无效配置由测试驱动拒绝，不能据此宣称原版内核自身具备这些保护。
- 本轮没有测试 Triton，也没有计时；通过仅适用于上述已覆盖范围。
