## S05. 操作语义与术语

store的输入是已经存在的K、V数据、目标索引indices及缓存。当前实验调用时这些张量已在GPU，操作是GPU内的数据复制，不是CPU到GPU传输，不是把K加工成V，也不是执行attention或生成文字。

以indices=[7,0,3]为例，所有下标从0开始：

| 输入行pid | pos=indices[pid] | 操作 |
| --- | --- | --- |
| 0 | 7 | K[0]→K缓存[7]，V[0]→V缓存[7] |
| 1 | 0 | K[1]→K缓存[0]，V[1]→V缓存[0] |
| 2 | 3 | K[2]→K缓存[3]，V[2]→V缓存[3] |

| 名词 | 当前例子中的准确含义 |
| --- | --- |
| B／batch | 本次输入的K/V行数 |
| D／width | 每行有效元素数，不是字节数 |
| capacity | 缓存槽数；与本次输入行数不同 |
| shape | 张量逻辑形状，例如(3,64) |
| dtype | 元素类型；FP16每元素2字节 |
| stride | 相邻下标在底层存储中的元素距离，例如(128,1) |
| gap | 本轮测试输入有效行后的额外空隙；由布局决定，不由空隙里是0或−1决定 |
| pid | 本人原型中当前program对应的输入行下标 |
| pos | 从indices中读出的目标槽编号 |
| ptr | 对应数据起始位置的指针；不是indices里的数值，也不等于0 |
| assert | 检查条件，不成立时报错；不负责复制数据 |

早期练习的缓存形状(8,2,128)表示8槽、每槽K/V两块、每块128个元素。中间2是该练习布局约定，不是所有PyTorch张量都有的固定维度。128个FP16元素占256字节，不是128bit。

## S06. 布局与地址计算：当前可重点出题

```text
连续输入K：K行0 | K行1 | K行2 | ...
输入V：独立于K的数据起点，同样按行组织

交错缓存：K槽0 | V槽0 | K槽1 | V槽1 | ...
分离缓存：K槽0 | K槽1 | ...；V槽0 | V槽1 | ...
带gap的输入：有效行0 | gap | 有效行1 | gap | ...
```

| 条件 | D=64时行距（元素） | D=128时行距（元素） |
| --- | ---: | ---: |
| 输入gap=0 | 64 | 128 |
| 本轮输入gap=64 | 128 | 192 |
| 交错缓存K/V视图，无额外填充 | 128 | 256 |
| 分离连续缓存K/V视图 | 64 | 128 |

仅改变缓存布局，输入布局不变，则需要改变目标地址算法，源地址算法不因此改变。源行距与目标行距不存在普遍的二倍关系。

当前列连续、K/V各自共享相应行距的地址关系：

```text
pos = indices[pid]
源元素偏移 = pid × 输入行距 + 列下标
目标元素偏移 = pos × 缓存行距 + 列下标
字节偏移 = 整个元素偏移 × 每元素字节数
```

Triton类型化指针加法按元素前进，FP16指针不需要在元素偏移后额外乘2；手算字节地址时才换算。原版CUDA若转换成字节指针，则必须对应其字节单位，不能混用两段代码的单位。

**例一：** D=64，连续输入，交错缓存，indices=[7,0,3]，pid=2，列下标4。

- pos=3。
- 源偏移2×64+4=132元素，即264字节。
- 目标偏移3×128+4=388元素，即776字节，分别相对于对应K/V缓存指针。
- 不是pid=3，不是pos=132，不需要遍历读取前两行。

**例二：** 只给输入增加gap=64，源行距变128。

- 同一元素的源偏移2×128+4=260元素，即520字节。
- 缓存不变，目标仍为388元素。

**例三：** 在例一基础上只改成分离连续缓存。

- 源仍132元素。
- 目标变3×64+4=196元素，即392字节。

相同dst_offsets加到不同的K/V缓存起点，在当前已分配的布局中指向各自数据区域。不能泛化为“任意两个不同指针都绝不会重叠”。

固定提交的MHAKVCache源码采用K/V分开的布局；练习交错布局不能直接当作模型实际布局。实际模型调用参数尚未采集。

## S07. 本人Triton原型与启动机制

以下摘录自10月2日14:08成功日志，省略了过期的初始注释和main提示。它是指导下实现，不是声称从空白独立写成的新代码。

```python
import triton
import triton.language as tl

@triton.jit
def store_kv_first(k_cache_ptr, v_cache_ptr, indices_ptr, k_ptr, v_ptr):
    pid = tl.program_id(0)
    cols = tl.arange(0, 64)
    pos = tl.load(indices_ptr + pid)

    src_offsets = pid * 64 + cols
    dst_offsets = pos * 128 + cols

    k_values = tl.load(k_ptr + src_offsets)
    tl.store(k_cache_ptr + dst_offsets, k_values)
    v_values = tl.load(v_ptr + src_offsets)
    tl.store(v_cache_ptr + dst_offsets, v_values)
```

关键解释：

- `indices_ptr + pid`先定位索引表第pid项的地址；`tl.load`再读取该处数值作为pos。不是给目标槽的数值加pid。
- `cols`是0到63，不包含64。它表示本program处理的列集合，不能据此认为有64个program或精确64个硬件线程。
- 64和128是当前固定输入／缓存行距，不能盲目套用到其他布局。
- 此例所有64列有效，因此没有mask；这不证明任意宽度都无需mask。
- 一个program在本设计中处理一整行K和一整行V；program不是单个thread。

调用发生在内核定义外。表达外部启动的示意代码如下：

```python
batch = k.shape[0]
store_kv_first[(batch,)](
    k_cache, v_cache, indices, k, v,
    num_warps=4,
)
```

B=3时grid=(3,)，pid分别为0、1、2。增加B需要匹配的输入行数、indices长度和grid，不需要复制三份内核源码。一次提交多个program不保证硬件同时执行所有program。

`num_warps=4`是启动配置，不是“4行输入”或“启动4次脚本”。Python里的结果检查for循环不负责GPU内核搬运。

原版与本人原型的分工不同：已核验的原版默认128线程/block、4个warp/block，每个有效warp处理一行，超出B的warp由条件跳过；本人Triton设计是一program处理一行。不能把两者映射直接等同。

在当前NVIDIA背景下，warp包含32个线程。它不自动保证线程访问相邻地址；相邻性来自地址设计。线程、warp、block概念可以出基础题，但寄存器、占用率和指令级性能尚未有本项目实测证据。

## S08. 已有检查代码与它不能单独证明的事

以下是已保存的检查，包装由教练提供，K/V比较来自学习者在反馈后的提交：

```python
import torch

def check_kv_targets(k_cache, v_cache, expected_k, expected_v, target_rows):
    for pid, pos in enumerate(target_rows):
        assert torch.equal(k_cache[pos], expected_k[pid])
        assert torch.equal(v_cache[pos], expected_v[pid])
```

调用方传入运行前的独立期望输入，以及结果的CPU快照。此处的Python pid变量用于枚举检查，不是调用GPU上的program_id。

`torch.equal`检查形状及元素值相等，返回布尔结果；这里不比较地址，也不完成复制。项目另外约定并核对dtype，不能只凭equal代替所有类型验证。

上述函数覆盖全部目标行的K/V值，但本身不检查未命中槽、只读输入或indices是否被改写。这些检查由完整运行器另行完成。只看到函数返回或打印PASS，不能脱离检查源码判断覆盖是否充分。

为什么要使用不同行、不同K/V内容：若测试数据全部相同，某些错行或K/V混用可能无法暴露。只打印每行前4个元素，也无法证明末列都写对。

完整流程：准备数据及期望值→调用算子→确保GPU工作完成并读取结果→检查→记录。实际记录框架会在断言前保存完整数组，便于失败后复核。

## S12. 性能与工具状态：不要出成已做过的成果题

- Nsight Systems曾在配置调整后捕获vector_add工具探针，不是KV写入内核的性能分析。
- Nsight Compute计数器仍有权限／资源限制，没有可靠的本项目占用率、寄存器或实际DRAM流量数据。
- 没有原版正式延迟表、自己的Triton延迟表、稳定加速比、优化消融或端到端吞吐结果。
- 不能仅因这个算子复制数据，就声称已经证明它是带宽瓶颈。
- 理论／未来测量题可问“如何排除首次编译”“如何保证公平”，但必须标为待学习设计题，不能问“你测得了多少”并编造答案。
