# M05基线收尾与后续优化路线

## 结论：M05首版原版baseline已完成

完成的是六个配置、固定版本、固定计时方式下的原版KV写入基线。已有原始数据、重复测量、复测、真实KV时间线与复现方法。后续自己的Triton版本可以据此开展对照。

“基线完成”指工程产物可用；不会自动意味着本人已经独立掌握所有测试代码、编译器或性能分析知识。此前看板把个人复述待答与交付状态混在一起，本次明确拆开：M05交付完成，理解能力继续在M06代码与结果中巩固。按交付权重M05为10/10、总项目30/100；这是交付记录，不是知识掌握率或实习录用概率。

## 1. 我们究竟测了什么

把已在GPU上的K、V两组数，按照indices指定的位置写进GPU上的KV缓存。我们测这一小步的时间，尚未测整个模型生成回答的速度。

可以把baseline理解为原版的成绩单：先把跑道、距离、计时方式都记录下来；自己的版本做好后，使用相同条件重新同场比较。原版与候选都要重新测，不能直接拿今天原版的一个数与另一日候选的一个数相除就宣称提速。

| 名称 | 本次含义 |
| --- | --- |
| B | 本次有多少行输入要写入，例如256行 |
| D | 每行有多少个数，例如128个；单位不是字节 |
| capacity=1024 | 缓存有1024个可用槽位；不表示每次都写满 |
| FP16 | 每个数占2字节 |
| 交错缓存 | 底层按K0、V0、K1、V1排列；K视图跨到下一K行需走2D个元素 |
| indices=0..B-1 | 本次依次写前B个槽，合法且不重复 |
| Graph | 预先捕获100次调用，重放这批工作；GPU Event区间除以100 |
| Eager | Python循环逐次提交100次调用；GPU Event区间除以100，可能包含提交间隙 |

上游固定提交：9a91cfafe754aa85daee49998176275667eb58f2。硬件为RTX 4070 Ti，Torch 2.9.1+cu128，CUDA12.8。输入与目标地址在同一进程内反复使用，未测冷缓存、分散随机槽位或整个模型。

数据准备、首次编译、预热、检查和保存不放进Event区间。结束标记后等待GPU完成再读取时间；100次总时间除以100，得到这个区间的每次平均值。它不是每个单独请求的耗时分布。

## 3. 今天的收尾结果补充了什么

**代表配置复测：** B256/D128的Graph=1.095680微秒/次，Eager=9.035680微秒/次，均落在旧三轮中位数范围内。原版代码未改，所以不能把比旧代表值低约6.1%叫优化；这正说明需要考虑运行波动。[本轮原始记录](logs/m05-closeout-results/run-k84pq53x/closeout.json)

**真实内核定位：** Nsight确认运行的是原版store_kv_cache，共41次，其中1次首次调用、20次预热、20次标记观察；从SQLite将20次GPU调用与标记范围内的CPU启动关联。该配置为64个block，每block128线程。[时间线审查](reviews/20261006-m05-kv-trace-review.json)

这次分析工具表中的90.9%，只是本次列出的GPU内核总耗时占比，不是整个模型或整个程序的时间占比。Profile采集有额外开销，WSL时间戳使用精度较低的兼容设置；其中的时长不替换Graph/Eager基线。[Nsight统计口径](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html)

**流量口径：** 读取K、读取V、写K、写V，共4份B×D数据；FP16每个数2字节，因此K/V逻辑读写量=8BD字节。B256/D128为262144字节。它不含indices，也不等于实际DRAM流量；当前反复使用小工作集，不能凭这个数字断言已经测出显存带宽上限。

温度、频率、实际DRAM计数未采集。三轮Graph中位数相对跨度约12.8%–37.5%；现有数据不足以确认几个百分点的小幅提速，也不足以单凭这个表确定性能瓶颈。

## 4. 接下来怎样提升

### M06：先把自己的版本做成可用的比较对象

| 小单元 | 要做出的东西 | 为什么要做 | 完成信号 |
| --- | --- | --- | --- |
| M06-01 宽度/行距参数 | 同一源码接收WIDTH、实际源行距、实际缓存行距 | 消除之前64宽代码配128宽数据的错误 | 同一源码通过D64/128四个对照用例 |
| M06-02 布局适配 | 支持约定内的分离缓存、交错缓存和行间空隙 | 行宽不等于行距，模型布局也不能靠猜 | 用真实stride寻址，全部目标与未命中存储正确 |
| M06-03/04 边界与入口 | 尾列mask、batch决定grid、空输入及支持范围检查 | 将学习例子变成有明确约定的可调用算子 | 约定范围通过；不支持输入明确处理 |
| M06-05 统一正确性 | 原版/v1接入已有测试集合 | 确认两个版本做的是同一件事 | 完整K/V、未命中、输入不变均通过 |
| M06-06 首次公平比较 | 同进程交替测原版/v1，统一数据、地址复用、预热与计时方式 | 首次知道自己的版本在哪里快、慢或无差别 | 六配置全部报告，样本和源码可追溯 |
| M06-07/08 解释与冻结 | 保存实际编译产物/元信息，写简短设计说明 | 能把源码、生成代码与运行结果联系起来 | 能解释program分工、地址、范围与一组结果 |

M06的目标首先是正确、可配置、可比较。v1比原版慢也有价值：它告诉我们后面应该调查什么，不需要为了让结果好看换计时方式。

### M07：有了对比，再做一项优化实验

1. 看原版/v1数据，选一个确实存在的差距；小batch与较大batch分别看。
2. 提出一个可以被结果推翻的解释。例如：本人的program分工是否为每行使用了过多执行资源，或访存组织是否存在问题。先列为假设，不直接写成瓶颈结论。
3. 只改变一个关键因素，形成v2。可考虑的方向是num_warps或每个program处理的行数；具体选择等v1数据与编译信息出来后决定。
4. 重新跑正确性，再让原版/v1/v2按相同条件交替重复测量。加速比=原版耗时/候选耗时，必须说明是哪个配置、哪种计时方式。
5. 保存变快、变慢和无收益的配置。收益不稳定时先保留不确定性；不从当前波动中挑几个数宣传提速。

### M08：最后检查模型是否受益

原版小模型运行和实际KV调用信息可以提前准备。只有模型调用确实接入自己的版本、输出正确且端到端测量完成，才能讨论模型速度变化。单算子更快不保证整条推理流程有明显提升。

## 5. 教练接下来如何带

每个小单元都按：讲清要解决的问题 → 展示当前相关代码 → 你修改少量关键行 → 一起看测试/性能结果 → 用自己的话解释结果。

环境、日志、批量运行、归档等外围可以由教练维护。内核设计和关键修改由你参与，指导与参考如实记录。不会因为脚本打印PASS就说你全部学会，也不会让同一个已完成实验反复运行代替讲解。
