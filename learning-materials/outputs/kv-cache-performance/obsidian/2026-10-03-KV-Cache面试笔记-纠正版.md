## 0. 我们的项目究竟在做什么

目标：以 mini-sglang 原版 KV 写入算子为参照，开发 Triton 实现，检查正确性，建立可复现的性能对比，再解释优化收益与适用范围。

当前内核的任务是：把已经位于 GPU 显存中的输入 K、V，按照 `indices` 写入 GPU 上的缓存槽位。它不负责计算 K/V、不执行完整 Attention，也不生成文字。

以 `indices = [7, 0, 3]` 为例：

| program 编号 pid | 读出的目标 pos | 读输入 | 写缓存 |
| --- | --- | --- | --- |
| 0 | 7 | K/V 第 0 行 | K/V 第 7 槽 |
| 1 | 0 | K/V 第 1 行 | K/V 第 0 槽 |
| 2 | 3 | K/V 第 2 行 | K/V 第 3 槽 |

这里的“一 program 搬一行”是本实验的设计，并非所有 Triton 算子的固定规则。

## 1. 先统一地址计算与单位

### 1.1 pid、pos、指针分别是什么

```python
pid = tl.program_id(0)
pos = tl.load(indices_ptr + pid)
```

- `pid`：当前 program 的编号。
- `indices_ptr`：索引数组起始位置的指针，不是数字 0，也不是数组第一个元素的值。
- `indices_ptr + pid`：定位到索引数组第 pid 个元素。
- `tl.load(...)`：读取该位置的值，得到目标槽位 pos。

通俗理解：先用 pid 找到分配表的某一格，再从这一格读出“送到哪个柜子”。

### 1.2 元素偏移与字节偏移

设 FP16 输入宽度为 64，连续输入行距为 64；交错缓存 K 行距为 128。对 `pid=2`、`pos=3`、列下标 `col=4`：

```text
源元素偏移 = 2 × 64 + 4 = 132
源字节偏移 = 132 × 2 = 264

目标元素偏移 = 3 × 128 + 4 = 388
目标字节偏移 = 388 × 2 = 776
```

`2×64` 表示跨过前两行的长度，直接计算地址，不需要逐个遍历前两行。

Triton 的有类型指针加法按元素计算，因此写 `k_ptr + 132`；不要再把 132 手动乘 2 加到 FP16 指针上。换算为字节是为了分析地址与流量。

### 1.3 width、stride、gap

- width：每行有效元素数。
- stride：沿某个维度移动一格，地址跨过多少个元素。
- gap：在指定布局中额外留下的间隔；它不是张量统一自带的一个属性。

连续独立 K 数组的行距可等于 width；交错 `K0,V0,K1,V1` 布局中，K 的行距可等于 `2×width`。V 是另一份有效数据，不能把 V 整段称为 padding。

仅对明确采用“每行有效数据后追加 gap”的二维布局，才有 `row_stride = width + gap`。一般应读取实际 stride，而不是永远按 width 或两倍 width 猜测。

## 2. Mask：哪些元素参与读写

### 2.1 可以直接确定的语义

以下是教学片段，不是已完成的通用项目内核。假设列连续、行距有效、pos 合法、源与目标分配足够：

```python
cols = tl.arange(0, BLOCK_SIZE)
mask = cols < width
src_offsets = pid * src_row_stride + cols
dst_offsets = pos * dst_row_stride + cols

values = tl.load(src_ptr + src_offsets, mask=mask, other=0.0)
tl.store(dst_ptr + dst_offsets, values, mask=mask)
```

当 `width=100`、`BLOCK_SIZE=128` 时，有效列是 0～99，共 100 个；屏蔽列是 100～127，共 28 个。

`tl.store` 的 mask 为假时，不向对应地址写入该元素。读取也需要适当的 mask；只给 store 加 mask，不能修复前面已经发生的越界 load。[Triton store 语义](https://triton-lang.org/main/python-api/generated/triton.language.store.html)

列 mask 也不能代替索引合法性检查：`cols < width` 并不能保证 `pos` 落在缓存容量内。边界保护需要覆盖所有可能越界的维度与操作。

### 2.2 元素数量不等于线程数量

Triton 描述一块数据，编译器负责将其映射到线程。128 个元素不意味着必然使用 128 个线程，更不能直接推出某个 warp 有多少线程实际读写。

如果额外假设“连续 128 列恰好按一线程一列分给四个 warp”，那么前三个 warp 对应 96 列，最后一个只有 4 列有效。这只是该假设下的推导，不是原代码编译结果的证据。

### 2.3 GPU 有分支，也可以使用谓词

GPU 支持控制流。编译器可能把部分短分支转成谓词执行：给指令附加一个条件，条件满足才产生相应操作。不能将其概括为“GPU 没有 if-else 跳转”。[CUDA 控制流说明](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-c-programming-guide/index.html#control-flow-instructions)

是否生成某条 SASS 指令、使用多宽的读写、如何处理尾部，需要结合实际编译产物分析。不能从一行 `tl.store` 就宣称一定生成 `STG.E.128`。

### 2.4 Mask 不能直接推出性能损失比例

100/128 是有效元素占比，不等于带宽利用率，也不等于程序只能达到满速的 78.125%。

被屏蔽的元素、线程映射、实际地址、指令宽度与内存请求共同影响开销。没有计数器与计时证据，不能预测“NCU 必定显示 10/32”“性能下降 70%”或“MBU 降到 30%”。

**面试表达：** 我先用 mask 保证尾部元素的读写语义。要判断它的性能影响，还需要检查编译结果和实际测量，不能直接用有效元素占比代替性能。

## 3. GQA、缓存布局与多维 stride

### 3.1 MHA、MQA、GQA 的区别

以 32 个 Query 头为例：

| 类型 | KV 头数量示例 | KV 数据量相对比例 |
| --- | --- | --- |
| MHA | 32 | 1 |
| MQA | 1 | 1/32 |
| GQA | 8 | 1/4 |

比例成立的前提是层数、缓存 token 数、head_dim、dtype 等保持相同。它计算的是 KV 数据量，而不是整张显卡总显存占用。

GQA 让一组 Query 头共享 K/V 头，在 KV 开销与模型质量之间做取舍。质量变化需要结合模型及训练评估；不能给 MHA 固定“100分”，也不能保证 GQA 精度不变、并发与上下文同时扩大四倍。[GQA 原论文](https://arxiv.org/abs/2305.13245)

### 3.2 多维 stride 的正确推导

假设某个教学缓存池连续存储，shape 为：

```text
(capacity, 2, Hkv, head_dim)
```

其中第二维 0 表示 K，1 表示 V。取 `Hkv=8`、`head_dim=128`：

| 维度 | stride，单位为元素 |
| --- | --- |
| head 内列 | 1 |
| head | 128 |
| K/V 通道 | 8×128 = 1024 |
| slot | 2×8×128 = 2048 |

这是这个连续布局的结果；转置、切片、padding 或采用另一布局后，应使用实际 stride。

每个 token 的 K 展平后有 `8×128=1024` 个元素。这里 head_dim=128，不等于之前教学实验“整行 width=128”。

### 3.3 公式必须与指针起点配套

从整个池的起点 `pool_ptr` 计算：

```python
offset = (pos * stride_slot
          + kv_idx * stride_kv
          + head_idx * stride_head
          + cols * stride_dim)
address = pool_ptr + offset
```

如果调用者已经提供指向 V 通道开头的 `v_cache_ptr`，则 V 通道的起始偏移已经包含在指针内，不要再加一次 `stride_kv`：

```python
v_address = (v_cache_ptr + pos * stride_slot
             + head_idx * stride_head + cols * stride_dim)
```

K、V 使用相同的相对偏移，也可以落在不同位置，因为各自指针的起点不同。

### 3.4 这不自动等于 Paged KV Cache

上面的 shape 只描述一个假设的槽位布局。分页缓存还涉及逻辑 token 到物理页及页内位置的映射。不能只看到 `capacity` 和多维 stride 就声称实现了分页管理。

练习里的交错布局也不是 mini-sglang 所有真实调用的默认约定。已有源码核对显示项目中的真实缓存池采用另一种维度组织与 K/V 分离方式；实际接入仍应核对运行时 shape、stride、dtype 和索引含义。[项目蓝图](../PROJECT-BLUEPRINT-20261002.md)

**面试表达：** 我先确认指针从哪里开始、每个维度跨多少元素，再计算地址。GQA 改变 KV 头数量，但具体内存布局由实现决定。

## 4. 特殊值填充与正确性验证

### 4.1 未初始化数据、空指针是两回事

`torch.empty` 通常分配未初始化的张量，不保证内容为零，也不能断言里面一定是别的用户留下的数据；某些确定性设置还会影响填充行为。不能依赖这些初始数值。[torch.empty 文档](https://docs.pytorch.org/docs/2.9/generated/torch.empty.html)

空指针描述地址是否有效；未初始化描述一个有效存储区的内容有没有被赋予规定值。不能用“显存只有 0 和 1”推导出“GPU 没有空指针”。

### 4.2 为什么不只检查目标行

完整的局部检查至少问三件事：

1. 目标 K/V 行是否等于对应输入？
2. 未命中的缓存区域是否保持原样？
3. 输入 K/V 和 indices 是否被意外修改？

有 padding 或底层共享存储时，还要检查视图之外但仍属于分配区的保护区域。仅检查视图，不一定覆盖整个底层存储。

### 4.3 特殊初值的作用

如果缓存初始是零，错误写入零可能不会被发现。使用与测试输入不同的有限哨兵值，例如 FP16 可精确表示的 `-1.0`，再保存快照，更容易发现误写。

原稿的 `-9999.0` 不能由 FP16 精确表示，会被舍入；这不妨碍同一个实际初值的前后比较，但必须认识到“写在代码里的十进制数”不总等于实际存储值。

这里称为“哨兵值填充”或“poisoning 测试”，不代表做了安全隔离证明。

### 4.4 检查模式示例

下面是模式说明，省略了真实内核调用，**不是可直接验收的完整脚本**。前提：有限输入、同 dtype、纯复制；target_rows 合法且不重复；所有比较张量放在同一设备。

```python
# 启动前：保存独立期望与输入快照
expected_k = k.clone()
expected_v = v.clone()
indices_before = indices.clone()
cache_before = cache_pool.clone()
target_rows = indices.cpu().tolist()

# 此处调用待测内核；确保完成后再观察结果
# ...

for pid, pos in enumerate(target_rows):
    assert torch.equal(k_cache[pos], expected_k[pid])
    assert torch.equal(v_cache[pos], expected_v[pid])

untouched = torch.ones(capacity, dtype=torch.bool,
                       device=cache_pool.device)
untouched[target_rows] = False
assert torch.equal(cache_pool[untouched], cache_before[untouched])

assert torch.equal(k, expected_k)
assert torch.equal(v, expected_v)
assert torch.equal(indices, indices_before)
```

此例假设 `cache_pool` 的第 0 维是槽位，并覆盖要检查的 K/V 区域。对于分离池、padding、额外保护区，应分别保存和检查对应存储，不能原样照搬这个索引表达式。

### 4.5 equal 与 allclose 不能混用概念

- `torch.equal`：形状和元素数值相等时返回真；它不是地址比较，也不要求 dtype 必须相同，因此 dtype 约束要单独检查。
- `torch.allclose`：允许指定的绝对、相对误差，适合有数值误差的计算结果。
- 当前有限数值、相同 dtype 的纯复制测试，可要求数值精确相等，不需要用容差掩盖差异。
- 数值相等不是逐位相等：`+0.0` 与 `-0.0` 数值相等；包含 NaN 的张量也有特殊比较行为。

若约定要求保留所有位模式，需要另行设计按位检查，并明确 NaN 与有符号零策略。[torch.equal 文档](https://docs.pytorch.org/docs/2.9/generated/torch.equal.html)

### 4.6 为什么不能承诺“100%查出越界”

前后状态比较仍可能漏掉：写入相同值、写后又恢复、写到检查范围以外、未改变输出的非法读取。检查通过只能说明被检查状态满足了这些断言。

可用保护区、不同背景数据、边界用例及专门内存检查工具补充；这些手段也不把有限测试变成对任意输入的证明。

还应故意破坏结果，确认检查器能拒绝错误。项目已有“错目标行、漏最后一列、交换 K/V、修改未命中区域或输入”等反例证据。

**面试表达：** 我同时检查目标、未命中区域与只读输入，并用故意破坏的结果验证检查器。通过说明这些用例满足约定，不代表已经覆盖一切内存错误。

## 5. 对齐、向量化与内存传输

### 5.1 三个层次要分开

| 层次 | 问题 |
| --- | --- |
| 单线程指令 | 这一条指令为该线程读写多少字节？ |
| warp 访存合并 | 参与线程的地址能合并成哪些请求？ |
| 缓存与显存 | 请求命中哪个层级，实际传输了多少数据？ |

16 字节向量访问是第一层的一种情况，不是显存控制器的统一“铲子大小”。对于计算能力 6.0 及以上设备，CUDA 最佳实践用覆盖 warp 请求地址所需的 32 字节事务数量解释全局访存合并；不能把它直接等同于每条指令一次 DRAM 传输或一个总线周期。[CUDA 合并访存说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)

### 5.2 对齐公式必须使用字节单位

程序中的 GPU 指针通常属于设备虚拟地址空间，不应直接称为“绝对物理地址”。用于对齐分析时：

```text
字节地址 = 起始字节地址 + 元素偏移 × 每元素字节数
```

若起始地址按 16 字节对齐，且字节偏移也是 16 的倍数，新地址仍然按 16 字节对齐。

FP16 每元素 2 字节，因此从这样的基址偏移 8 个元素相当于偏移 16 字节；偏移 1 个元素相当于偏移 2 字节。后者仍可满足 FP16 标量的 2 字节对齐，但不满足 16 字节向量访问所需的对齐。

这是“某条访问的起点是否满足其要求”，不是“所有标量元素必须按 16 字节对齐”。

### 5.3 未对齐不是统一的安全降速

必须结合访问的数据类型、指令与编译器掌握的信息判断。编译器可能生成较窄访问，但不能假设它总会修复错误的对齐承诺。

CUDA 文档特别提醒，不满足自然对齐的 8/16 字节读取可能产生错误结果。因此不能承诺“JIT 会保证不崩溃、只让速度变慢”。[CUDA 大小与对齐要求](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-c-programming-guide/index.html#device-memory-accesses)

也不能统一推出“两次事务、性能减半”。额外请求数与性能损失取决于具体地址、参与线程、访问宽度和缓存行为。

**面试表达：** 对齐既可能关系到某类访问是否合法，也可能影响访存效率。我会先确认访问要求，再用编译产物和测量判断代价。

## 6. JIT、AOT 与自动调优

### 6.1 JIT 是什么

AOT 通常在运行前编译；JIT 在运行过程中需要某个版本时编译。AOT 也能利用模板、常量和目标架构优化，不能称为必然低效的“盲盒”。

Triton 会根据类型、编译期常量及相关特化信息生成并缓存相应版本。它不会先读懂 K/V 数组里的所有数值，再自动设计最优算法；也不是任何 shape 改变都必然重新编译。[Triton jit 接口](https://triton-lang.org/main/python-api/generated/triton.jit.html)

### 6.2 三件不同的事

| 工作 | 含义 |
| --- | --- |
| 编译与特化 | 按当前类型、常量等信息生成程序版本 |
| 内核融合 | 把多步计算放进同一个内核，可能减少中间数据写回 |
| 自动调优 | 对提供的候选配置计时，选择测得较好的配置 |

`@triton.jit` 不会自动把周围任意 PyTorch 操作融合，也不等于自动搜索所有启动配置。显式写在同一内核中的 `y=a*x+b` 可能不需要把中间乘积写回显存，但最终输出 y 仍需按约定存储。

自动调优通常另行使用 `@triton.autotune(configs=..., key=...)`。其结果是指定条件下候选集合中的选择，不是证明得到全局最优。由于候选会重复执行，修改数据的内核还需要考虑状态恢复。[Triton autotune 文档](https://triton-lang.org/main/python-api/generated/triton.autotune.html)

### 6.3 开发者仍负责什么

地址、mask、输入约定、启动范围、并发写冲突、同步与正确性验证都需要开发者负责。能编译不等于正确，正确也不等于高效。

编译器可能进行常量折叠、循环展开或向量化，但“地址对齐”不能单独证明一定选择某条 128 位指令，更不能证明它一定最快。

**面试表达：** JIT 帮助生成适合当前特化条件的内核；我负责表达正确的工作划分与访存，并通过测试和计时评估实现。

## 7. 有效带宽：先定义口径，再谈利用率

下面是后续基线工作的分析口径，当前还没有相应实测数据。

对 B 行、每行 D 个元素、每元素 s 字节的纯 KV 复制，如果只统计输入 K/V 读取与目标 K/V 写入：

```text
逻辑有效字节数 = 2 × B × D × s（读取）
               + 2 × B × D × s（写入）
               = 4 × B × D × s

有效带宽 GB/s = 逻辑有效字节数 / 时间秒 / 10^9
```

例如 B=3、D=64、FP16，逻辑 K/V 流量为 1536 字节。这个口径不包括索引读取、缓存事务放大等；若计入索引等开销，应在报告中另行说明。

逻辑字节数不等于实际 DRAM 流量。反复访问同一小块数据可能命中缓存，特别小的内核也可能主要受启动开销影响。因此，将有效带宽除以显存理论峰值所得比值，不能自动当成硬件 DRAM 利用率。

正式基线要明确：计时区间、预热与编译排除、同步方式、重复采样、输入与缓存复用方式。原版和自己的实现必须采用可比较的口径。[CUDA 有效带宽说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#effective-bandwidth-calculation)

本机是 RTX 4070 Ti，不应把其他架构或 HBM 平台的结论直接作为本机实测结果。

## 8. 原笔记主要说法对照

| 原说法 | 纠正后的表述 |

| shape 带 capacity 就是 Paged KV | 还需明确页表和逻辑到物理的映射 |
| empty 里一定是其他用户的数据 | 内容未保证初始化，不能推断来源 |
| equal 是逐位检查 | 它比较形状和数值；位模式、dtype等要求另行检查 |

### 9.2 理解自检

| 问题 | 回答必须包含的要点 |
| --- | --- |
| pid=2为何不直接写缓存第2行？ | 目标来自indices[2]，本例为3 |
| FP16源偏移132为何是264字节？ | 元素数乘每元素2字节；指针表达式仍按元素 |
| 换成分离缓存要改什么？ | 核对目标指针与实际stride；不假设永远2×width |
| 为什么128宽测试不能直接跑64宽硬编码内核？ | 数据准备与地址约定不匹配，会漏写或写错位置 |
| D=100用128列时mask做什么？ | 只让有效列参与相关读写；不能由此声称具体线程数 |
| 为什么填-1比全零更有用但仍不完备？ | 更易发现某些误写；同值写入和未检查区域仍是盲区 |
| 为什么equal通过不代表内核绝对安全？ | 只证明这些数据和断言满足条件，不能覆盖所有访问 |
| 为什么对齐不等于性能翻倍？ | 需要区分指令、合并访存、缓存与真实耗时 |
| jit和autotune有什么区别？ | 编译与测试候选配置是不同工作 |
| 下一步怎样证明优化有效？ | 相同约定下先正确，再用可复现计时对比并解释适用范围 |

能换一组数字推导、修改小段代码并解释错误原因，比只复述答案更能说明掌握。

### 9.3 学习优先顺序

1. 巩固指针、pid/pos、shape/stride、元素与字节单位。
2. 能解释并修改核心读写及检查；明确支持范围。
3. 推进 M05 正式基线，记录可复现的计时与数据。
4. 用参数化、边界测试和真实布局适配完善 Triton 实现。
5. 根据测量提出优化假设，再用编译产物或性能工具追查原因。
