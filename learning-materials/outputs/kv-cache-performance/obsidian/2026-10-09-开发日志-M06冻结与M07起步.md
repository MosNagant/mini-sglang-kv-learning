### 13:42：M06-04，完成公共调用入口

文件为 `experiments/triton_store_api.py`。本人在提示后完成/修正的关键部分：

```python
if indices.shape != (batch,):
    raise ValueError("INDEX_COUNT: one destination is required per input row")

if batch == 0:
    return

# 索引值合法性校验之后启动
store_kv_v1[(batch,)](..., num_warps=4)
```

上面是机制摘录，省略号不是完整可执行源码。`(batch,)`表示只有一个维度的形状或grid；`batch`来自输入张量的行数。

结果：**4个非空GPU用例、2个空输入零启动用例、18种非法调用预期拒绝。** 检查包括索引数量、形状、类型、设备、步长、重复/越界索引和不支持的存储重叠等。

这一步的意义是让外部调用者知道什么能输入、错误发生时怎样反馈。B=5时一次KV启动包含5个program；B=0时封装返回，KV启动次数为0。

证据：[公共入口归档](../modules/M06/evidence/04-wrapper/status.json)。

## 3. 这次测出来的结果

计时范围：RTX4070Ti，FP16/int32，C=1024，交错缓存，input_gap=0，连续唯一目标索引，重复相同地址。源行距D，缓存行距2D。软件为Torch2.9.1+cu128、Triton3.5.1；固定mini-sglang提交为 `9a91cfafe754aa85daee49998176275667eb58f2`。

下表是Graph结果。代表耗时先取每进程30区间的中位数，再取三进程中位数的中位数。**速度比=原版耗时÷v1耗时，大于1代表该统计值下v1更快。**

| B | D | 原版代表耗时µs | v1代表耗时µs | 速度比 | 三轮里v1更快的轮数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 64 | 0.900800 | 0.949600 | 0.9486 | 0/3 |
| 1 | 128 | 1.092480 | 1.137120 | 0.9607 | 0/3 |
| 16 | 64 | 1.087360 | 1.057440 | 1.0283 | 2/3 |
| 16 | 128 | 1.118880 | 1.180160 | 0.9481 | 0/3 |
| 256 | 64 | 1.170240 | 1.111200 | 1.0531 | 1/3 |
| 256 | 128 | 1.033920 | 1.156480 | 0.8940 | 1/3 |

**当前结论：v1在限定范围内正确，但没有稳定快于原版的证据。**

尤其B256/D64，代表速度比虽然为1.0531，三轮配对比值却是0.8692、0.9319、1.0531，前两轮更慢，不能据此写“稳定提升5%”。两个代表数的比值与逐轮配对比值是不同统计方式。

Eager的18组配对里v1都更慢，但它包含不同Python/JIT调用路径与主机提交间隙的影响，不能将全部差异归因于GPU内核。完整成绩见[M06性能报告](../modules/M06/RESULTS.md)。

尚未取得：稳定优化收益、NCU运行时硬件计数器、实测DRAM带宽、真实模型端到端提升或AMD GPU结果。

## 4. 今天要串起来的运行机制

```text
准备K/V、indices与缓存
    → 公共入口读取shape/stride并检查合同
    → 非空时启动一次KV内核，grid=(B,)
    → 各program读取自己的pid和indices[pid]
    → 按源/目标stride算地址，用mask保护有效列
    → 搬完整一行K/V
    → 在计时外检查完整结果
```

性能实验使用预先验证过的受信任启动入口；公共入口的GPU索引值校验可能同步，不能悄悄只算到某一方的耗时里。

| 容易混淆的量 | 当前应如何区分 |
| --- | --- |
| B与pid | B是本次输入总行数；pid是某一行的编号 |
| D与stride | D是有效元素数；stride是相邻行开头的元素距离 |
| gap与缓存交错 | input_gap描述输入行额外间隔；K/V交错是目标布局，两者独立 |
| launch与program | 一次launch可以包含B个program |
| BLOCK_SIZE与num_warps | 前者是逻辑列块大小；后者是每program的warp配置 |
| 检查通过与性能改善 | 搬得对是必要条件，速度是否改善要由公平计时回答 |

## 6. M07的第一步已经确定什么

本人预测原话：

> 更快，因为一个warp工作量不算多

候选方向：保持一program搬一行，只研究 `num_warps=4 → 1`。这称为启动配置调优；此刻候选还没有修改或运行。

教练补充的待验证解释：每行工作量较少，1个warp可能已经够用；减少warp也可能降低行内并行度，因此“更快”必须实测。改变warp数不减少应搬运的元素，也不改变B决定的program数量。
