## 1. 从一行K/V，连到真实的一次聊天

一行K与对应的一行V，在这个写入路径中，保存一个token在当前注意力层算出的两组数字。token是模型处理的文字片段，不一定等于一个汉字。每个注意力层有自己的K/V；后续计算可复用已经保存的历史K/V。[缓存原理](https://huggingface.co/docs/transformers/en/cache_explanation)

```text
文字变成token → 当前层算出K/V → store按indices保存 → 注意力读取历史与当前K/V
                                  ↑
                         我们当前优化的局部步骤
```

本实验的源与目标都在GPU显存中。store负责保存已算好的值；得到完整文字回答还需要模型中的其他计算。

### B：本次实际交给算子的token行数

| 场景，先忽略额外填充 | 本次输入 | B |
| --- | --- | ---: |
| prefill：处理提示词 | 一个请求有256个尚未处理的token，本次全部处理 | 256 |
| 合并多个请求的prefill | 两个请求本次分别处理100、156个新token | 256 |
| 普通decode：逐token生成 | 一个请求，本轮处理一个新token | 1 |
| 多请求一起decode | 16个请求，本轮各处理一个新token | 16 |

B不是最终想生成的字数，也不固定等于请求数。历史已有1000个token、本轮只新增一个token的普通decode，写入的B仍可为1；历史缓存的读取工作属于后续注意力计算。

这些是规模示例，不是已经运行了相应模型的证据。实际调度还会切分长提示词、复用已缓存前缀；CUDA Graph也可能补齐执行规模。因此应读取真正传给算子的输入行数，不能只数活跃请求。

固定源码的链路是：scheduler按每个请求的新增token数展开input_mapping；同一映射产生input_ids和out_loc；注意力后端把k、v、out_loc交给store_kv。这里的out_loc就是写入目标索引。

### D：每行K有多少个有效数字，V也有同样多

D描述这一行实际要搬的元素数。一次调用处理B对行；“一行”不是“一次调用”。

在固定mini-sglang版本的这条路径中：

```text
D = 当前GPU负责的KV头数 × 每个头的维度
```

例如8个本地KV头、每头128维，整行D是1024。这个例子只是解释公式；旧笔记已有[多头展开示意](2026-10-03-KV-Cache面试笔记-纠正版.md#3-gqa缓存布局与多维-stride)。

模型结构与本卡分工固定时，聊天变长通常增加缓存中的token行数，D通常不变。当前测试D=64/128是小宽度测试，不能默认代表真实模型的整行宽度；也不能把head_dim=128直接当作D=128。

### indices与capacity：分配位置与可用槽数

沿用已有映射：B=3、indices=[7,0,3]，三对输入行分别保存到7、0、3号缓存槽。capacity表示这个缓存池可用的token槽数；B是这次写多少行，capacity是能放多少行。

源码里还存在一个容易误读的变量：store.py中的num_tokens取自k_cache.shape[0]，在这里表示缓存槽容量，不是本次输入B。不能只根据变量名判断语义。

真实MHAKVCache采用一个大分配中的K区和V区，底层形状是：

```text
(2, 层数, 页数, 每页槽数, 本地KV头数, 每头维度)
```

它把K/V分开存放，不是我们教学池的逐槽K/V交错，也不意味着一定做了两次独立显存分配。单层展平后capacity=页数×每页槽数，D=本地KV头数×每头维度。真实模型的dtype、输入stride、调度形状仍要在模型运行时采样确认。

源码定位：固定提交9a91cfafe754aa85daee49998176275667eb58f2；[缓存池](../../github-upload/current-wsl-20261006T131451Z/python/minisgl/kvcache/mha_pool.py)、[注意力层](../../github-upload/current-wsl-20261006T131451Z/python/minisgl/layers/attention.py)、[调度器](../../github-upload/current-wsl-20261006T131451Z/python/minisgl/scheduler/scheduler.py)、[store包装](../../github-upload/current-wsl-20261006T131451Z/python/minisgl/kernel/store.py)。

### 这次特别补正gap所在的位置

旧笔记已解释width/stride/gap。本项目M04的具体gap是**输入K/V每行尾部额外预留的元素位置**，底层输入形状为(B,D+gap)，取前D列给算子；其余位置填-9供检查，缓存未命中位置初值为-1。

因此，输入行距=D+gap；交错缓存行距=2D，分离缓存行距=D。缓存layout与输入gap是两个独立测试维度，V数据本身不能叫作输入padding。

M05六配置全部使用输入gap=0、交错缓存。M04证明gap=64用例写入正确，不等于M05已经测过gap=64的性能。未来改变gap或缓存布局，必须为原版和候选同时建立该条件下的新对照。

## 3. 一次计时从哪里开始，到哪里结束

你曾写过的100次Eager计时核心如下。它说明计时机制；最终六配置运行器还包含Graph分支、检查、交替采样和归档。

```python
def measure_once(call, start, end):
    start.record()
    for _ in range(100):
        call()
    end.record()
    end.synchronize()
    return start.elapsed_time(end) / 100
```

前提：start/end是enable_timing=True的CUDA Event；本实验把标记和算子工作放在同一CUDA stream，准备与首次编译已完成。

| 代码 | 它做的事 |
| --- | --- |
| start.record() | 把开始标记放入GPU工作流；不是此刻读取CPU墙钟 |
| call() | 调用包装函数，提交原版store工作；Python返回不保证GPU已完成 |
| end.record() | 把结束标记排在这批工作之后 |
| end.synchronize() | CPU等待结束事件完成，然后才继续读取结果 |
| start.elapsed_time(end) | 读取两个GPU事件之间的时间差，单位毫秒 |
| 除以100 | 得到这一批100次调用的平均每次耗时 |

这里应写end.synchronize()。call是普通Python可调用对象，本实验的call没有synchronize方法。Event的记录、等待和毫秒返回值见[PyTorch 2.9文档](https://docs.pytorch.org/docs/2.9/generated/torch.cuda.Event.html)。

完整顺序为：

```text
准备数据、缓存与独立期望
→ 首次调用，完成JIT/初始化
→ 等待并检查
→ 预热，等待预热完成
→ [开始Event → 100次调用 → 结束Event]
→ 等结束Event完成 → 读取区间时间÷100
→ 每一对Graph/Eager采样后检查结果，检查位于两个计时区间之外
→ 保存源码、配置、样本与统计
```

方括号才是本例Event区间。数据准备、首次JIT、预热、检查、打印与保存都不放进去。预热是减少首次执行因素的影响，不是保证GPU从此没有波动。

**为什么“等待在区间外”和“区间可能混入空隙”同时成立？**

end.synchronize的CPU等待不是再加进结果的一段耗时；结果取自GPU上的两个标记。但如果GPU已经跑过开始标记，而CPU还没及时提交下一次工作，GPU等待后续任务的空隙可以落在标记之间。因此Event区间不自动等于剥离所有空隙后的纯内核执行时长。

1毫秒=1000微秒；0.004毫秒=4微秒。先确认单位，再比较数字。

## 4. Graph与Eager：同一算子的两种提交方式

| 方式 | 本项目每个计时区间内的操作 | 主要区别 |
| --- | --- | --- |
| Eager | Python循环调用原版100次 | 每次由主机逐次提交，可能产生提交空隙 |
| CUDA Graph | 重放一张预先捕获了100次原版调用的图 | 减少重复的主机提交工作 |
| 两者共同点 | 区间耗时都除100 | 都反复使用当前配置下相同的数据地址 |

Graph可以理解成预先整理好的工作单，之后提交整份工作单。图捕获与初始化放在正式计时之外。它不会把我们的100次store自动变成一个融合内核，也不意味着GPU执行没有任何调度或等待成本。[NVIDIA CUDA Graphs说明](https://developer.nvidia.com/blog/cuda-graphs/)

之前约8微秒的Eager与约1微秒的Graph，都来自同一个原版算子。这个差别说明执行方式会影响测量，不是本人Triton已经加速了原版。

后续比较必须用同口径：原版Graph对候选Graph，原版Eager对候选Eager。分别报告，不交叉相除。

## 5. 一个成绩数字是怎样产生的

对“一个配置、一种执行方式”：

```text
100次调用的区间总耗时 ÷ 100
            ↓
         1个样本
            ↓
每进程采30个样本，取中位数
            ↓
开3个新进程，得到3个轮中位数
            ↓
再取中位数，得到报告中的代表值
```

因此，30×100×3表示采样层次，不是得到了9000个独立单次调用延迟。最终保存的是区间平均值，不能从这些数组直接声称获得单次请求P99。

全部六配置、两种方式、每配置3轮，共36个样本数组、1080个区间平均样本。

## 6. 为什么B、D差很多，六组耗时却都约1微秒

先确认单位：“微秒/次”是一次调用完成全部B对K/V行的平均耗时。B=256时已经包含本次256对行，不要再乘256。

### B增大：原版增加并行工作

固定原版默认128线程/block、4个warp/block，每个有效warp负责一对K/V行。因此：

| B | block数量ceil(B/4) | 有效搬运warp数 |
| ---: | ---: | ---: |
| 1 | 1 | 1 |
| 16 | 4 | 16 |
| 256 | 64 | 256 |

相当于货物多了，同时增加班组，而不是同一班组顺序多跑256趟。多个block可以并行执行；实际同时驻留和执行多少受资源与调度限制，不能声称64个block必然同时完成。

这是原版CUDA的分工。不要直接套成“一个Triton program固定就是一个warp”。

### D增大：这两个宽度都只需一次源码复制循环

对FP16，一行K在D64时占128字节，在D128时占256字节。原版warp::copy分别选每lane 4、8字节的包，两个宽度的K复制各一轮，V再各复制一轮。

D翻倍并没有让这两个例子的源码循环数翻倍。但一轮搬运更多数据仍有成本；源码循环次数相同不能证明最终机器指令数、访存事务数或耗时完全相同。

原版实现定位：[store.cu](../../github-upload/current-wsl-20261006T131451Z/python/minisgl/kernel/csrc/jit/store.cu)、[warp.cuh](../../github-upload/current-wsl-20261006T131451Z/python/minisgl/kernel/csrc/include/minisgl/warp.cuh)。

### 测量波动也足以打乱简单排序

B1/D64三轮中位数约0.876～1.075微秒；B1/D128约0.880～1.213微秒。范围重叠，不能因代表值0.888小于1.075就断言“128宽比64宽更快”。

当前现象与小工作量下固定执行成本、并行工作、地址复用等解释相容。我们没有采到可确认具体瓶颈的硬件计数器，不能写成已经证明启动受限、缓存全命中或DRAM饱和。Graph已减少重复CPU提交，也不能把这张Graph表约1微秒的平台直接归因于Python慢。

## 7. Nsight这次到底补了什么

计时报告回答“在规定方式下多久”；时间线补充“实际调用了哪个内核、启动了多少次、执行规模是什么”。

10月6日真实KV trace中，store_kv_cache有41次：

```text
1次首次调用 + 20次预热 + 20次标记观察 = 41次
```

SQLite关联确认20次GPU调用对应标记范围内的CPU启动；代表配置为64个block、每block128线程。这与B256、每block处理4行的源码相符。NVTX标记给一段工作命名，本身不是另一种算子，也不能仅凭CPU标记时间段推断所有异步GPU工作的边界。

报告中的90.9%表示原版store占该统计表列出的GPU内核总时长的比例；它没有把Python等待等整个程序时间作为分母，也没有运行完整LLM。因此不能说KV写入占大模型推理的90.9%。

Profile表中的约0.992微秒不替换Event基线。这次还存在兼容时间戳精度较低、额外CUDA事件追踪可能增加开销的限制；NCU硬件计数器未取得。定位到内核不等于已经定位性能瓶颈。证据见[时间线审查](../reviews/20261006-m05-kv-trace-review.json)与[M05收尾报告](../M05基线收尾与后续优化路线-20261006.md)。

## 8. 怎样让后续“优化了多少”有可信含义

主要看同条件下的每次调用耗时；同样B/D的数据更快搬完，对应的行吞吐也更高。FP16下K/V逻辑读写量为8BD字节：读K、读V、写K、写V各一份，每元素2字节，不计indices。有效带宽=逻辑字节量/耗时；它不能直接当实际DRAM带宽。B256/D128为262144字节，除以基线1.166880微秒约224.654 GB/s，这是逻辑有效口径，未证明DRAM实际流量或利用率。

比较公式：

```text
加速比 = 原版耗时 / 候选耗时
耗时减少比例 = (原版耗时 - 候选耗时) / 原版耗时
```

仅作算术示范：把原版1.166880微秒与“假设候选0.90微秒”比较，约为1.30倍加速、耗时减少23%。0.90不是已测结果，当前尚无本人Triton性能对照。

正式比较时需要：

- 原版和候选做相同工作：B、D、dtype、索引、布局、stride以及检查要求一致。
- 两者分别完成首次编译、预热和正确性检查，统一Graph/Eager与地址复用方式。
- 在可比环境下交替采样，重复多轮，保留原始结果；不能拿另一日候选的一次最小值直接除以旧baseline。
- 全部选定配置一起报告，包括变慢与无明显收益的情况；差异与波动相当时保留不确定结论。
- 改小B或D、少搬数据不算同一任务提速。改变gap/layout时，也要为原版采同条件的新对照。

目前的小规模原版已约1微秒，不能预先保证Triton明显更快。下一步先完成可配置、可比较的v1，再决定调查哪项成本。整模型的tokens/s与响应时间要等真实接入测试，单算子加速比不能代替整机收益。
