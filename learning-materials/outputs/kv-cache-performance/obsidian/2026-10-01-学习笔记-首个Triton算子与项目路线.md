## 3. 今天这个程序到底在干什么

一句话：**把已经存在 GPU 内存里的 K、V，按照索引表写入指定的缓存行。**

这里没有计算注意力权重，也没有生成文字。K/V 是推理中会被后续注意力操作使用的数据；今天的数字是为了容易检查而人为生成的测试输入。

```text
准备输入 K/V 和目标索引
        ↓
准备缓存，全部填成 -1
        ↓
调用 GPU 内核进行写入
        ↓
等待 GPU 完成
        ↓
保存完整结果，检查所有目标行和未命中行
```

打印每行前 4 个元素只是方便观察；本次 PASS 来自整行及其他检查，覆盖了打印没有展开的元素。

### 3.1 固定小例的输入条件

| 对象 | shape | stride（元素单位） | dtype |
| --- | --- | --- | --- |
| 输入 K | `(2, 128)` | `(128, 1)` | float16 |
| 输入 V | `(2, 128)` | `(128, 1)` | float16 |
| 总缓存 | `(8, 2, 128)` | 连续分配 | float16 |
| K 缓存视图 | `(8, 128)` | `(256, 1)` | float16 |
| V 缓存视图 | `(8, 128)` | `(256, 1)` | float16 |
| 索引表 | `(2,)`，值为 `[5, 1]` | 每项一个整数 | int32 |

`(8, 2, 128)` 的含义：8 个缓存位置，每个位置在本例中分为 K 和 V 两区，每区有 128 个数。这个 2 来自本例的布局约定，并非所有 PyTorch 张量的第二维都表示 K/V。

**128 是元素数量，不是 128 bit。** 当前每个 float16 数占 2 字节，所以单个 K 行占 256 字节。一个缓存位置的 K+V 合计 512 字节。

本例总体缓存分配是 `8 × 2 × 128 × 2 = 4096` 字节。显卡物理显存、这次申请的缓存容量、这次实际写入量是三个不同数量。

### 3.2 内存排列

```text
输入 k：     [K输入行0：128个数][K输入行1：128个数]
输入 v：     [V输入行0：128个数][V输入行1：128个数]

总缓存：     [K槽0][V槽0][K槽1][V槽1] ... [K槽7][V槽7]
每个 K/V 区：128个数
```

输入 K 的下一行起点相隔 128 个元素；缓存中下一行 K 的起点相隔 256 个元素，因为中间还有一行 V。切出 K 视图并不会把底层夹着的 V 搬走。

V 是另一份输入数据，并非“复制 K 之后得到的结果”。测试里 `v = k + 1000` 是为了让两份数据容易区分，不是模型产生 V 的通用规则。

### 3.3 这次的结果

| 输入 | 索引值 | 写入位置 | 缓存中的前 4 个数 |
| --- | --- | --- | --- |
| K 输入行 0 | 5 | K 缓存行 5 | `[10, 11, 12, 13]` |
| V 输入行 0 | 5 | V 缓存行 5 | `[1010, 1011, 1012, 1013]` |
| K 输入行 1 | 1 | K 缓存行 1 | `[138, 139, 140, 141]` |
| V 输入行 1 | 1 | V 缓存行 1 | `[1138, 1139, 1140, 1141]` |

缓存位置 `0、2、3、4、6、7` 的 K/V 保持全部为 `-1`。源 K/V 和索引表也没有被修改。

## 4. 今天实际运行的 Triton 核心

以下为成功运行日志中的核心代码，去掉了模板提示注释，没有新增功能。模板、地址指导和 K 读写示范由教练提供；用户填写 K/V 读写并根据审查修正变量名。它是第一版学习实现，不是完全独立从零写出的通用算子。

```python
import triton
import triton.language as tl


@triton.jit
def store_kv_first(k_cache_ptr, v_cache_ptr, indices_ptr, k_ptr, v_ptr):
    pid = tl.program_id(0)
    cols = tl.arange(0, 128)
    pos = tl.load(indices_ptr + pid)

    src_offsets = pid * 128 + cols
    dst_offsets = pos * 256 + cols

    k_values = tl.load(k_ptr + src_offsets)
    tl.store(k_cache_ptr + dst_offsets, k_values)
    v_values = tl.load(v_ptr + src_offsets)
    tl.store(v_cache_ptr + dst_offsets, v_values)
```

运行器使用 `grid=(2,)`，即两个 program；此次设置 `num_warps=4`，不代表已经找到了最佳配置。

### 4.1 program、pid、cols、pos

| 名字 | 在当前代码中的意思 |
| --- | --- |
| program | 一次逻辑工作实例；本设计每个实例处理一行输入的 K 和 V |
| `pid` | 当前实例的编号，同时用来选输入行 |
| `cols` | 行内元素编号 `0..127`，不是数据值 |
| `pos` | 从索引表读出的缓存目标行号 |

`pid` 是 0 和 1，是因为这次启动了两个 program；不是 API 永远只能返回两个编号。`tl.program_id(0)` 中的参数 0 表示取启动网格第 0 轴的编号。

`tl.arange(0, 128)` 不包含 128，一共 128 个位置。当前这些位置都合法，因此这个固定小例没有用 mask；不能直接据此声称任意宽度也安全。

program 不能直接等同于一个线程或一个固定 32 线程的 warp。当前的“一 program 一行”是一种设计选择，不是保证最快的规定。

### 4.2 `indices_ptr + pid` 中的加号

```python
pos = tl.load(indices_ptr + pid)
```

按动作拆开理解：

1. `indices_ptr` 是索引表首元素的 GPU 内存地址。
2. `+ pid` 表示从起点向后偏移 `pid` 个元素，得到所需那一项的地址。
3. `tl.load` 从这个地址读取整数。
4. `pos` 接到读出的整数，也就是目标缓存行号。

```text
indices = [7, 3]

indices_ptr + 0 → 第0项的地址 → load读出7
indices_ptr + 1 → 第1项的地址 → load读出3
```

可以用熟悉的 `pos = indices[pid]` 理解整体作用；实际 Triton 仍使用上面的指针写法。

**地址加法不等于给表中数字加法。** `pid=1` 不会把表改成 `[8, 4]`，也不会让 `pos` 自动变成上一项加一。

假设表的起始字节地址是 1000，当前 int32 每项占 4 字节，则两项的地址为 1000 和 1004。`indices_ptr + 1` 指向第二项，类型化指针加法会按元素大小换算；代码不用再乘 4。1000 只是讲解用地址，没有读取过本机的实际地址数值。

学习状态：用户已经正确预测 `[7, 3]` 的对应关系；指针地址、偏移与读取值的区别仍需在后续代码里巩固。

### 4.3 源地址和目标地址

```python
src_offsets = pid * 128 + cols
dst_offsets = pos * 256 + cols
```

统一公式是：**行号 × 行距 + 行内位置**。

- 源行号是 `pid`，输入行距为 128 个元素。
- 目标行号是 `pos`，缓存视图行距为 256 个元素。
- 两者都按元素计数，分别相对于各自指针起点。

对实际通过的 `[5, 1]`，取 `pid=1`、`cols` 中的列 4：

```text
pos = 1
源元素偏移 = 1 × 128 + 4 = 132
目标元素偏移 = 1 × 256 + 4 = 260
```

以字节距离手算时，FP16 分别是 `132×2=264` 字节、`260×2=520` 字节。但实际代码把元素偏移加到 FP16 指针上，不再手动乘 2。

先前 CUDA 例子中的“lane × 8 字节”按搬运片段算偏移；这里 `cols` 按单个元素编号。两套单位不能混写成“行号 × 元素数 + 列号 × 字节数”。

### 4.4 同一个 dst_offsets 为什么没有让 K/V 相互覆盖

```python
tl.store(k_cache_ptr + dst_offsets, k_values)
tl.store(v_cache_ptr + dst_offsets, v_values)
```

当前 K/V 视图的起点不同：一个指向 K 区，一个指向 V 区。按当前合法行距和列范围加上同一组偏移，分别落到该缓存位置的 K 区和 V 区。

“不同指针就永远不重叠”不是通用规则；这里不重叠由具体起点、步长和合法访问范围共同保证。

### 4.5 写入与检查各做什么

| 语句 | 动作 |
| --- | --- |
| `tl.load(地址)` | 从给定位置读出数值 |
| `tl.store(地址, 数值)` | 把数值写到给定位置 |
| `torch.equal(k_cache[5], k[0])` | 比较两份张量的内容是否相同 |
| `assert ...` | 条件不成立时让检查失败 |

今天 `dst_offset` 漏写了最后一个 `s`，实际定义的是 `dst_offsets`；这处变量名已修正。失败及审查记录保留，成功运行的源码中缩进和拼写均正确。

### 7.1 备选方向一：KV 写入的 CUDA/Triton 对照与访存优化

**优先级：最高，建议默认保留。**

- **项目问题：** 不同 batch、行宽、输入步长和目标分布下，哪一种工作划分更合适，为什么？
- **复用内容：** 现有 mini-sglang、原版 CUDA、本人 Triton、所有正确性和基准数据。
- **本人新增贡献：** 根据测量提出可推翻的假设，修改读写组织或 program 分工，报告收益和回退。若实际 JD 要求 CUDA C++，增加本人 CUDA 版本，并明确重排时间。
- **成品标准：** 实现源码、统一支持域、全量测试、可复测数据、一次假设验证、限制说明。
- **可对照的岗位类型：** GPU 算子、GPU 软件、性能工程、计算库开发；具体是否匹配取决于 JD。
- **当前机器：** 可继续用已经验证的 4070 Ti 环境，不需要因岗位名称变化而重装。

这条路线继续使用 Triton 作为工具，但作品的能力标签是“GPU 算子工程与性能分析”，不是只会某种语法。原版 CUDA 代码阅读也不能代替本人 CUDA 实现经历。

### 7.2 备选方向二：GPU 算子的正确性与性能回归工具

**优先级：高，适合转向 GPU 软件验证或性能工具方向时选择。**

- **项目问题：** 换了实现或依赖版本，怎样自动发现写错、越界风险、输入被修改或性能回退？
- **复用内容：** 当前断言、未命中检查、固定版本、源码和结果快照。
- **本人新增贡献：** 参数化用例生成、独立参考结果、失败样本复现、重复测量和噪声判定；对故意构造的错误版本证明测试能抓到问题。
- **最小范围：** 先让同一个 KV 操作接入原版 CUDA 与本人 Triton，不一口气接很多算子。
- **成品标准：** 一条命令生成测试/对照报告，可重放失败输入；显示通过、失败、跳过及原因。性能告警门槛须结合波动建立，不能单次变慢就判退化。
- **当前机器：** 可使用现有 GPU。若后来加入 GPU CI，需要实际 GPU runner，不能假设普通免费 CI 自带显卡。

pytest 官方支持将一组检查用于多组参数，为这种工具提供基础机制；上面的完整回归工具是项目设计建议，不是现成测试框架自动替我们完成的工作。[pytest 参数化文档](https://docs.pytest.org/en/stable/how-to/parametrize.html)

### 7.3 备选方向三：单卡 LLM 推理服务的延迟—吞吐分析

**优先级：中，实际 JD 偏 AI Infra 或推理服务时考虑。**

- **项目问题：** 请求变多、输入变长或共享前缀变化时，用户等待与系统吞吐如何变化，瓶颈在哪里？
- **复用内容：** mini-sglang 背景、KV 生命周期、GPU 测量和记录方法，后续既定的小模型整机验证。
- **新增知识：** prefill/decode、排队与批处理、首 token 延迟 TTFT、后续 token 间隔/平均每 token 时间、请求整体延迟、吞吐与分位数。
- **本人新增贡献：** 受控工作负载生成、请求时间点记录、排队/执行分解、单因素实验与基于证据的一项改进；不能只运行别人脚本并贴成绩。
- **最小范围：** 先验证小模型能在当前显存与软件环境运行，再选择一个正式框架，如 SGLang。若目标岗位另有要求再选 vLLM；不同时维护两套服务来凑内容。
- **成品标准：** 可复现负载、延迟—吞吐曲线、原始请求记录、瓶颈证据及改动前后结果。服务端指标不能直接由孤立内核计时推算。
- **代价：** 比前两项多一层服务和模型环境，当前尚未验证，应在目标岗位明确时再排期；现在不下载模型作为下一步前置。

SGLang 官方区分在线服务、离线吞吐和静态 batch 等不同层次的测量，并提供 TTFT、TPOT、ITL 与吞吐等服务指标。这支持把服务性能另立为一个有明确测量边界的项目；不能用离线数据冒充在线表现。[SGLang Benchmark and Profiling](https://docs.sglang.io/docs/developer_guide/benchmark_and_profiling)

### 7.4 备选方向四：KV 内核的 HIP 移植与 AMD 实测

**优先级：有条件；取得合适的 AMD GPU 和实际需求后再选。**

- **项目问题：** 同一个操作移到 HIP/AMD 后是否仍正确，哪些实现假设需要调整，表现如何？
- **复用内容：** KV 契约、独立测试、测量协议、已有 CUDA 对照。
- **本人新增贡献：** 完成所需的 C++/HIP 内核及调用适配，检查依赖和架构假设，在目标 AMD 设备上运行和分析。
- **成品标准：** AMD 设备上的实际编译/运行记录、正确性、测量配置及局限；只做 API 替换或只在 NVIDIA 上验证，不足以交付“AMD 性能验证”。
- **硬件边界：** 目前只有已经验证的 NVIDIA 4070 Ti，不能用它声称获得 AMD/ROCm 实测。需要额外硬件或远程资源，费用及访问方式在实际选定后再安排。
- **本月安排：** 暂不替换当前主线，不自动安装 ROCm，也不承诺 10 月 25 日前并行完成。

AMD 官方说明 HIP/HIPIFY 可用于 CUDA 移植，但并非把 API 名字换掉就一定完成；还可能需要手工适配和性能调整。上述小范围移植方案是基于这一能力与我们现有代码的建议。[AMD HIP 移植指南（固定文档版本 7.2）](https://rocm.docs.amd.com/projects/HIP/en/docs-7.2.0/how-to/hip_porting_guide.html)
