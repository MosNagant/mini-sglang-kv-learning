# M03与M04集中验收

目标：说明输入、布局与调用路径；原版CUDA通过统一正确性集合。本人Triton固定原型留到M06升级后复用这套检查。

## M03-01：搬什么，搬到哪里

K和V是两份已经算好的数据，store按indices复制到缓存。不是把K加工成V；本实验调用时输入和缓存已经在GPU。

| 输入下标pid | indices[pid]即pos | 对应操作 |
| --- | --- | --- |
| 0 | 7 | K[0]→K缓存[7]，V[0]→V缓存[7] |
| 1 | 0 | K[1]→K缓存[0]，V[1]→V缓存[0] |
| 2 | 3 | K[2]→K缓存[3]，V[2]→V缓存[3] |

本文全部使用从0开始的下标。“下标1”就是平常数的第二行。

## M03-02：行宽、行距、单位

- shape=(3,64)：三行，每行64个数。
- dtype=FP16：每个数2字节，一行128字节。
- stride=(64,1)：跨一行移动64元素，跨一列移动1元素。
- 有行间空隙时，shape仍可为(3,64)，stride变为(128,1)。

**元素偏移=行下标×行距+列下标。字节偏移=整个元素偏移×每元素字节数。** Triton类型化指针加法用元素偏移。

连续输入下标1、列下标4：1×64+4=68元素，68×2=136字节。`1×64+4×2`混用了两种单位。

## M03-03：两种布局

```text
交错：K槽0 | V槽0 | K槽1 | V槽1 | ...
分离：K槽0 | K槽1 | ...；另一缓冲区为V槽0 | V槽1 | ...
```

每槽K或V有64元素时，交错K/V视图各自行距128，分离视图各自行距64。K/V指针起点不同，相同相对偏移并不指向同一数据。

固定提交的[模型缓存源码](https://github.com/sgl-project/mini-sglang/blob/9a91cfafe754aa85daee49998176275667eb58f2/python/minisgl/kvcache/mha_pool.py)将K/V分开；模型实参仍需M08实际记录。

输入下标1对应pos=0，列下标4在交错K缓存里的偏移是0×128+4=4元素。源地址用pid，目标地址用pos。

## M03-04：谁调用谁

```text
PowerShell → WSL测试脚本 → 准备输入/缓存/独立期望值
→ 原版Python store_cache → JIT加载并调用CUDA
→ 等GPU完成 → 检查全部数据 → 保存记录
```

原版默认128线程/block，4个warp/block，每个有效warp处理一行，超出batch的warp由条件判断跳过。本人Triton原型则由外部grid=(batch,)启动，用pid区分输入行。这是两种实现的分工方式。

`for pid,pos in enumerate(target_rows)`是检查循环，不负责GPU搬运。一次脚本可测试许多用例；旧的2/2是两个实现各通过一个用例，不是处理两行。

`torch.equal`比较完整数据的数值，不比较地址。不同地址可有相同内容。本例K/V内容不同，交换expected_k和expected_v应该失败。
