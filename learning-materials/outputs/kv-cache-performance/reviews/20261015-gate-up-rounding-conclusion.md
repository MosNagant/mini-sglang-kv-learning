# Gate/Up 精度差异：舍入边界审查结论

本次只读取已有 49 号输出、84 份真实模型输入、权重及保存的 FP64 oracle；没有运行 GPU、修改候选或放宽验收。完整统计在 [rounding-analysis.json](../logs/m08-gate-up-experiments/run-20261015-044242-mca3s3gj/rounding-analysis.json)，604 个争议坐标的精确计算在 [rounding-analysis-details.json](../logs/m08-gate-up-experiments/run-20261015-044242-mca3s3gj/rounding-analysis-details.json)。

## 观察结果

84 份样本各有 6144 个线性输出 Z，总计 **516,096 个元素**。四个 GEMV 候选分别得到相同的统计：

| 比较 | 元素数量 |
|---|---:|
| Triton 与原版 cuBLAS FP16 Z 不同 | 490 |
| 相差一个 FP16 ULP | 467 |
| 相差超过一个 ULP | 23，最大 9 ULP |
| 原版与保存的 FP64 点积舍入到 FP16 后不同 | 445 |
| Triton 与保存的 FP64 点积舍入到 FP16 后不同 | 290 |

不能把“9 ULP”直接理解成很大的绝对误差。例如 step 1、layer 18、gate 第 515 列，两个输出约为 `4.9651e-5` 和 `5.0187e-5`，差约 `5.36e-7`；这里很接近零，FP16 间距很小。

## 用精确整数排除 oracle 自身的舍入疑问

每个有限 FP16 数都可以写成整数乘以 `2^-24`。把输入与权重这样转换后，以 Python 任意精度整数做乘法及求和，就能得到精确点积 `整数 × 2^-48`。再比较相邻 FP16 候选与精确值的距离，按 ties-to-even 选最近值。

对“任一候选或原版不等于 FP64 舍入结果”的并集 **604 个坐标**进行了这个重算。保存的 FP64 oracle 舍入结果与精确整数点积的最近 FP16 值在这 604 个坐标全部一致。分析器另有 [8 项 CPU 控制](20261015-gate-up-rounding-controls.json)，覆盖正负中点、ties-to-even、符号零和抵消。

在 Triton 与原版不同的 490 个坐标中：

| 精确点积参照下的比较 | 数量 |
|---|---:|
| Triton 更接近精确点积 | 326 |
| 原版更接近精确点积 | 164 |
| 只有 Triton 得到正确舍入的 FP16 | 314 |
| 只有原版得到正确舍入的 FP16 | 159 |
| 两者都不是正确舍入结果 | 17 |

其中 284 个坐标距离 FP16 舍入中点不超过 `0.01 ULP`，174 个不超过 `0.001 ULP`，没有恰好落在中点的情况。很小的 FP32 累加差异就足以让这些结果舍入到中点的另一侧。其余差异还可能涉及抵消等数值敏感性；本审查没有恢复 cuBLAS 内部执行次序，不能把每个差异逐项归因到某条指令。

## 为什么不能靠“打开 FMA”保证修复

保存的 direct r4/w4 PTX 已经包含 `fma.rn.f32` 累加链，随后有 shuffle/add 归约。它并非漏用了 FMA。有限 FP16 操作数的单个乘积本身可以精确表示为 FP32；变化主要要结合累加顺序、归约树及最终舍入调查，而不是假设启用一个 FMA 开关就会与 cuBLAS 完全一致。

即使换成更精确的累加方法，也不能保证重现原版输出：这里原版自身有 445 个元素不同于保存 oracle 的最近 FP16 值。**数学误差更小与复现指定实现的输出，是两个不同的目标。** 本次数据并不支持“所有差异都是 Triton 写错了”，也不证明整模型偏差无关紧要。

## 对下一步的约束

若保持当前整模型验收标准，应继续将没有通过该标准的候选留在研究分支。尝试复刻 cuBLAS 归约需要其实际算法与运算顺序证据，目前没有这项证据，也不能承诺一次参数修改就能解决。

更稳妥的独立优化方向是保留已验收的原始数值运算，研究提交、预分配或 Graph 组织的开销，并重新做完整正确性与同场性能比较。该建议本身不代表已经获得稳定加速。

范围限制：只对争议并集 604 个点做精确整数点积；其余元素的统计基于保存的 FP64 oracle。本审查没有验证 AMD、模型质量、任意输入或整模型误差传播的单一原因，也没有改变学习者独立掌握评分。
